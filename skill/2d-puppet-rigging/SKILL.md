# 2D 傀儡模型绑定（Iki = Live2D 的开源替代）

## When to Use

用户要把立绘做成会眨眼、张嘴、转头、能被语音驱动的 2D 角色（桌宠、分身 App 的形象、vtuber）；
要「Live2D 那种效果」但不想碰 Cubism 的授权。本机路线：开源 **Iki**（`refs/iki`：`packages/editor`
文档与命令栈、`packages/engine` 播放、`packages/format` 校验、`packages/mcp` 切层/绑定），
成品是 `.iki`（JSON），播放器是 80KB 的独立页，不背编辑器。

没有现成图时，找图走 `free-asset-sourcing` 第三步半（角色定稿锚点 + 档案站 `.md` 索引）。
要**自己生成**绑定用素材（A-pose 立绘、纯白底、改姿势去道具）时：**有参考原图就走
Qwen-Image-2.1 的「参考图 + 指令编辑」**（体型 / 画风 / 配色直接继承原图，不需要体型词）；
只有手上没有任何原图时才退回 SDXL + COCO-18 骨架，而那条路已知两头翻车（不加体型词→细长腿，
补 `chubby`→肥胖侏儒）。两条路线的完整配方、指令七段式、白底归纯白的分阈值表、以及
「用户已认可一版时先 diff 提示词再调参」的规矩，见 `references/apose-generation.md`。
**参考图的表情会和道具一起被搬过来**：原图在吃 / 在哭 / 在困，生成的 A-pose 仍然是那个表情。
指令里必须显式写出目标表情并逐项否定原表情（`cfg=1` 下负面提示不生效，只能往正向写）。
⚠️ `scripts/apose_check.py` 的三段 75% 阈值**只对骨架图标定**，Qwen 参考图会把真 A-pose 误判成
NOT-A-POSE（空隙只有几像素），不要拿它否决 Qwen 的产出。配套脚本（可直接跑，不必重写）：
- `scripts/apose_check.py`：数每行角色连通段判定 A-pose（三段≥75%），支持 `--batch <glob>` 整批筛
- `scripts/bg_whiten.py`：背景 flood-fill 归纯白，自带四角 + 轮廓外 3px 环验收
- `scripts/zoom_face.py`：按角色 bbox 裁头区 / 嘴部放大拼条（`--mode mouth|face`），逐张验收表情
- `scripts/measure_motion.py`：对连拍帧序列算各区平均运动量 + 出热图，判「某部件到底动没动」用它，不要看缩略拼图问 VLM
- `scripts/measure_underlayer_leak.py`：统计某件 bbox 内的肤色像素数，判「转动时有没有露出额头/皮肤底层」（拆层开缝的硬指标）

**「一组 N 张」不等于 N 次独立采样。** 独立生成出来的是 N 个不同的角色（服装层数、发型轮廓、
体型宽窄都在漂），单张能看，整组放一起会被判「规格不统一」而退回。开工前先问清用户要哪种：
N 个候选（独立采样 + 三重筛 + 留一个编号备选池，方便事后单张替换）还是一组风格一致的图
（1 张合格源图 + img2img 衍生，denoise 0.45–0.55）。前者预算按 30–40 张生成量算，合格率只有 20–40%。
选图对切层成败影响很大：**正面、对称、手不遮脸、背景纯色**的图能一次 `passed:true`；
略侧转、手挡脸、复杂背景的图会在眼框/嘴框上反复打转。

## 先分清素材，别把能力说大

| 素材 | 能做到 | 入口 |
|---|---|---|
| 命名分层 PNG（face/eye_L/mouth…）或分层 PSD | 全套绑定：眨眼、张嘴、头转、视线、物理摆动，秒级 | 编辑器「导入图层组」 |
| 单张成品图 | 整张作为一个部件：能摆位、能整体变形，**不会眨眼张嘴** | 本机已加的「导入单张图片」(见下) |
| 单张成品图且要会动 | 必须先切层；切层**不含 ML**，要关键点 | `@ikijs/mcp` cut 管线 + 人/agent 读网格标点 |
| 单张成品图，且要求「被刘海遮住的额头、眼睑下的眼白也完整」 | 单图切层做不到，要生成式拆件（补画是**部分**的，实测 36–54%，别承诺全补） | See-through 出 17–23 层 PSD：`references/see-through-deployment.md`；拿到 PSD 后可直接丢现成消费端自动绑定：`references/psd-consumer-tools.md` |

**不要**把「单张图导入」当成交付「会动的模型」，也不要对用户承诺「上传一张图自动就动」——
上游的自动切层是「给点 → 按颜色和形态学切」，官方描述里明确写坐标由 agent 读网格给出。
本地也没有可用的二次元人脸关键点模型（照片域的 DWPose 在动漫图上实测约 30%）。

### ⛔ 单图切层（`@ikijs/mcp` cut）只算调试件，不能当 Live2D 交付

cut 管线按颜色 + 形态学硬切，稳定只出 **14 层左右**，语义上就这些：
`face / nose / mouth / eye_L / eye_R / iris_L / iris_R / lash_* / lash_lower_* / hair_front / hair_back / body`。
它**不认识四肢、不认识尾巴**；头发只有前/后两层；眼白、虹膜、睫毛虽分层但没有独立的闭眼/闭口差分；
而且每层是像素硬切、互不重叠，部件一动就露底。

用户验收这类交付时是逐项点名的：「头发没有分层、眼睛 嘴 四肢 尾巴 都没做分层、又把撕裂的坑踩了一次」，
并直接判定「还不如上一个 live2d」。这不是调参能救的，是产出结构缺层。

**开工前的自检**：要交「会动的 2D 模型」时，先能回答「头发 / 眼白 / 虹膜 / 睫毛 / 眉 / 嘴 /
上衣 / 手 / 腿袜 / 鞋 / 尾巴 各自独立成层吗」。有一条答不上，就不要走 cut 管线，
直接上 See-through 出 17 层 PSD（`references/see-through-deployment.md`）+ 现成消费端自动绑定
（`references/psd-consumer-tools.md`）。

**已有 See-through PSD 时先复用，不要重跑弱的管线。** 工程里如果已经躺着一套 17 层 PSD
（`out/layerdiff_output/*.psd`），那它就是可用的上游资产；另起一套单图切层等于把已付的成本丢掉，
换来一个层数更少、还带层缝的结果。开工先 `ls` 一遍 layerdiff/psd 目录再决定路线。

### ⛔ 自己重建 PSD 时：`PSDImage.new(mode="RGBA")`，否则只有顶层有物理

用 `psd_tools` 改写层（拆细、改名、加派生物理层）时，`mode="RGB"` 建出来的 PSD 只有 3 个 channel，
逐层写 RGBA 图像时 **alpha 被静默丢弃**，每层都变成整张不透明，一层盖一层。
症状极具欺骗性：`composite()` 看着“完整”，绑定诊断也正常，但**只有最上面几层头发参与物理**，
尾巴 / 裙 / 腿 / 身体全部静止——很容易误判成「这工具不给那些部件摇摆」。

必须做两条验证，缺一条就不要拿去绑定：

```python
assert psd.channels == 4                                   # 3 = alpha 已丢，重写
for l in psd.descendants():
    if l.is_group(): continue
    cov = (np.asarray(l.topil())[:, :, 3] > 150).mean() * 100
    assert cov < 50, f"{l.name} 覆盖 {cov:.2f}% —— alpha 丢了"
```

正常层覆盖是 0.0x–11%；**100.00% 就是坏的**。同一套层在 RGBA 下尾巴运动量从 0.28 直接到 10.36。
拆分规则、层→物理种类对照、以及「哪几层值得拆、哪几层拆了更差」，见 `references/psd-consumer-tools.md`。

### ✋ 部件「不动」先调每层「奥行き」，不要拆层

层卡片 ▸ 展开后只有「濃さ / 奥行き 0–2」两个旋钮，`奥行き` 就是该层参与视差与跟随的量，
默认值直接决定谁不动：`tail` **0.5**、`back hair` **0.55**（全场最低）→ 尾巴与后脑勺几乎静止；
`front hair` **1.28**（最高）→ 一动就夸张。这跟层块大小无关，调完也不用重出 PSD。

先做这一轮再谈别的：`tail`→1.6~2.0、`back hair`→1.2~2.0、`legwear`/`footwear`→1.3~2.0、
`headwear`→1.45（耳/头饰）、`front hair`→1.0（收夸张）、`topwear`→0~0.1（衣服不许跟着晃）、
`pBust`=0（不要胸部摇曳）。17 层完全不拆、只调这一轮的实测：呆毛 34.68 / 耳朵 16.97 /
前发 36.96 / 后脑勺 32.54 / 尾根 12.96。

**拆层是最后手段**：`front hair` 拆出 `ahoge`/`side hair`、`back hair` 拆三段，都会在额头与后脑留下
**肉眼可见的横向断缝**（用户会直接判「头发被切开了」），且 `_2`/`_3` 规范化成同族后仍可能被并进同一物理组。
确实必须拆时才拆，层内重叠 30–40 px，拆完当场量缝。验收顺序是**无缝 > 会动**。

## 要独立枢轴就自己写 `.iki`，别再调别人的自动绑定

自动绑定的枢轴是它按连通域自己算的：尾巴横向伸出时钉在尾鳍尖、`legwear` 没有摇摆属性、`mouth` 会自己缩放。
调 `奥行き` 只能放大跟随量，改不了枢轴。「尾巴整条从根摆、梢部摆幅最大 / 腿要动 / 嘴不许乱缩」这三条
在这个页面上是做不到的——**不要在原地拉滑杆，直接手写 `.iki`**：`parts` 是自由数组，每块都能有
自己的 deformer 和枢轴。完整配方（坐标系、atlas 打包、pivot 换算、pivot 表、物理参数与实测数字）见
`references/iki-hand-rig.md`。

写这条路之前先记住三条，否则会白跑好几轮：

1. **物理只在 `IkiMotion.update()` 里 tick。** 只 `player.setParameter(...)` 时所有物理输出参数永远是 0、
   画面完全静止，极易误判成「模型写错了/引擎不支持」。必须每帧**先写外部驱动（头/身角度）、再 `motion.update(now)`**，
   顺序反了物理读到的是上一帧角度。
2. **`physicsChains` 在本机引擎里等于冻结**（只跟 anchorDeformer 的矩阵，静态 anchor 下实测摆幅 0.01–0.08 度）；
   把链输出喂回自己的 anchor 直接报 `feeds its own anchor deformer chain (feedback)`，
   而两个 `physics` 互相串也报 `feedback loops are not supported`。
   可用配方是**一个弹簧驱动同一个输出参数 + 几级 matrix deformer 挂这个参数、`from/to` 递增、`parent` 串联**，
   角度在父链上累积出鞭梢感。
3. **后台标签页把 `requestAnimationFrame` 和 `setInterval` 一起节流**（实测 rAF 回调 1 秒不触发、
   900 ms 的 interval 只跑 1 次），于是所有参数回读都是 0。读之前先
   `cdp("Page.bringToFront")` + `cdp("Emulation.setFocusEmulationEnabled", enabled=True)`，
   并确认 `canvas.width` 已等于模型画布（不是 300×150）。

4. **必须有 head / body 两级 matrix 总成。** 缺了它，转头时只有「绑了 `ParamAngleX` 的件」在动，
   脸和五官原地不动而头发在动 —— 视觉上就是头和头发被撕开。`def_Head` 枢轴放脖子，挂脸/五官/
   头饰/前后发/耳/呆毛（没有自身物理的件直接 `part.deformer = "def_Head"`）；`def_Body` 枢轴放腰，
   挂手/裙/腿/鞋/尾巴。有物理的件把自己的 deformer 用 `parent` 串到这两级下面：先整体跟着走，再叠加局部形变。
5. **连续的一整块 = 一个 part，绕根部一个 matrix deformer 转，不要拆段。** 拆成根/中/梢三段给「各自的枢轴」
   是这条路线最容易踩的坑：段间是独立矩形，一转就错位露缝（用户判「撕裂感又出来了」）；
   三段绑同一参数又必然同相位刚性转动（用户判「变成了单图层了」）。整块绕尾根转时尾尖离枢轴最远、
   摆幅天然最大，正是想要的效果且结构上不可能有接缝。实测 `ParamTailSway` ±30 → 绕根 ±24°，
   尾鳍尖左右各甩出取景框，VLM 复核「没有明显接缝或断层」。
6. **前发 / 后发不许拆，而且要在切层脚本里就合并回去；唯一例外是呆毛。** 从 `front hair` 里切出
   `side hair`、把 `back hair` 切三段，都是硬切：静态合起来等于原图，各自绕不同枢轴一转，切口就露出
   **底下的脸 / 后发**（露的是下层而不是透明背景，所以「透明底量缝」查不出来）。用户的原话是
   「前发还有侧面有很明显的开缝 露出额头底层」。正解是不切：`front hair` / `back hair` 各保持一整块。
   **呆毛也一样不许拆。** 曾以为它长在头骨外侧、下方压着头发而不是脸皮，切在根部下方 30 px
   （实测根 y≈128、切 y=160、重叠 4156px）就安全 —— 实测不成立：呆毛绕根一转，那段重叠跟着转走，
   而前发顶边在 y=130 处只有 **52px 宽**，让开就是黑色背景。用户判「头顶又出现了分离的地方」，
   VLM 也指出「帧40 根部下方及左侧出现巨大三角形黑色空洞」。**重叠是双重绘制，不是补画**，
   救不了这种错位。要给呆毛独立动画只能先在前发上补画根部衬底（under-paint）再切；
   不补就让它跟着整片前发摆，把这个代价主动讲出来。
7. **「有没有露底层」用肤色像素数判，不要问 VLM。** 统计该件 bbox 内的肤色像素数，**摆动帧不得高于静止帧**
   （实测 59 帧最大增加 0 px = 无缝；VLM 对一两像素的缝会答「没有异常」）。
   直接跑 `scripts/measure_underlayer_leak.py <帧目录>`，或传 `--bbox x,y,w,h` 指定要查的那一件。

8. **切之前先数连通域：1 个连通域 + 无颜色分界 = 没有可切的结构，任何切线都是我自己画的。**
   判据不止「切口会被什么挡住」，还要先问「素材里到底有没有这个分界」。开工先跑
   `scipy.ndimage.label(alpha>30)` 数一遍（逐层实测表与配方见 `references/layer-splitting-rules.md`）。
   细分只有两种合法依据：**连通域**、或**颜色/语义**；按坐标切（x 直线、每行中点、y 阈值、
   补一道阴影再沿阴影切）一律是几何面，用户会直接点出来：「你裁切的还是以几何面而不是贴着素材裁切导致的」。
   实测 `legwear` 整层只有 **1 个连通域**（43389px, x[578,763]）—— 两条腿从大腿根到脚踝连成一块，
   按 x 切、逐行找中点切、补接触阴影再切，切出来都是「一坨被分两半」外加每条腿各少一块。
   这种层要独立动画只有两条路：**先补画**（inpaint 出两腿之间真实的空隙）把素材变成 2 个连通域、
   再按连通域分离 —— 那是画图不是绑定，必须单独跟用户确认，不能顺手在切层脚本里硬切；
   或者走第 28 条「同一 part 内部 warp 网格分左右」，那条不用补画也不存在错位露缝。
   反过来，切口被什么挡住决定「切了会不会露」：额头/鬓角下层是**脸皮**、后脑下层是**后发** → 不能切，
   切了必露底色，补边也救不了（露的是下一层内容，不是透明）；**大腿根下层是裙摆、且裙下沿 y 高于切口** →
   即使可切也看不见缝。先判定再动手，能省掉好几轮「拆了→露缝→合回去」。

9. **必须联动的一套件挂同一个 deformer（共用一个枢轴），不要各自挂总成。** 腿与鞋、手与袖口、头与耳饰
   都是一套；一挂 `def_Body`、一挂自己的弹簧，就是「腿动了鞋没动」的视觉分离，用户会直接点名
   **但「腿要独立摆」不成立时不要硬拆**：`legwear` 实测只有 1 个连通域（见第 8 条），按 L/R 拆出来是
   素材不支持独立腿时，先按第 28 条试「同一 part 内部 warp 网格分左右」（不用补画、不可能露缝）；
   连网格也做不了，才腿+鞋整块挂同一个 deformer、小幅度摆，并明确告诉用户「要真独立必须先补画两腿之间的空隙」。
   同一件事还会以「一件衣服被 See-through 切在两层」的形式出现：围裙上胸落在 `topwear`（白色占 72.6%）、
   裙面落在 `bottomwear`，两层挂不同 deformer 就是「一个摆一个不动」。按颜色拆出独立 `apron_top`，
   再和 `bottomwear` 挂同一个 deformer。**开工先查「这套件是不是被上层管线切成了两个层名」。**

10. **物理输出 `scale` 按「实测摆幅 → 目标角度」反算，不要凭感觉给。** binding 的 `from/to` 是角度：
    `实际角度 = (参数摆幅 / 参数半量程) × binding 角度`。看得见的次级运动约 8–20°；实测耳朵 `scale` 26
    只摆 1.39°（等于没动）、150 才摆 8.57°。给完必须回读实测摆幅再换算，不要拿代码里的数字当结论。
    标定对照表见 `references/iki-hand-rig.md`。

11. **单独验某个 deformer 时，先加 `?nodrive=1` 开关跳过驱动与 `motion.update()`。** 否则
    `motion.update()` 每帧都会把物理输出参数重算一遍，`setParameter` 手动设的值立刻被覆盖，
    回读到的永远是物理值（实测设 25 回读 4.39），会误判成「deformer 没生效」而白改一轮。

12. **层构建脚本里「原样抄回」清单会静默盖掉你拆好的层。** 典型结构：先
    `out["apron_top"] = cut(tw, white)` / `out["topwear"] = cut(tw, ~white)`，末尾还有一个
    `keep_as_is = [...]; for n in keep_as_is: out[n] = layers[n]`。只要清单里重复出现派生层名，
    就把拆好的结果覆盖回整层原图。症状极具欺骗性：脚本不报错、层数对、派生层覆盖率也正常，
    但**视觉和像素差都没变**（实测换完 order 差异只变化 1px）—— 很容易误判成「层级思路错了」而去改方向。
    守则：清单只放没派生过的层；循环后当场 assert 派生层像素数 < 原层像素数；改完按第 13 条验证。
13. **「改动是否真的落地」用像素差 delta 判，不要读代码自证。** 结构改动（换 order、换父级、换枢轴）
    后重拍同姿态截图对比，若该区差异只变化 0–2px，说明改动没生效（被覆盖 / 页面缓存 / 没重新部署），
    回去查而不是继续调参；delta 明显（例：鞋区 3423→1812）才算真改到。
    对比必须 **1:1 原生尺寸**：把 1100 的截图放大到 1280 再 diff 会凭空造出七万「模型有原图没有」的假像素，
    看着像整身错位。先 `cdp("Emulation.setDeviceMetricsOverride", width=1290, height=1290,
    deviceScaleFactor=1)`，确认 `canvas.width == model.canvas.width` 再截。

    **diff 只能算「两边都有内容」的像素**（`both = (原图非白底) & (渲染非黑底)`），这条漏掉会让整轮结论反转：
    原图是白底、播放器是黑底，背景像素差恒为 200+，不屏蔽就会被当成「模型漏画」——实测脚区
    32490px 里 90% 是背景，屏蔽后真实差异 **1916px**。同理「模型有原图没有」也要先 `~om & sm`，
    否则白色背景自己就被算成多出来的内容。

    **缓存要用 CDP 关掉，且 cache-bust URL 必须保留原参数。** 只 `Page.reload` 时文件 MD5 变了、
    四次截图却字节完全相同（被当成「改动无效」排查了好几轮）。配方：
    `cdp("Network.enable")` + `cdp("Network.setCacheDisabled", cacheDisabled=True)`，再
    `Page.navigate` 到带时间戳的 URL。⚠️ 拼 cache-bust 参数时**不要覆盖掉 `?nodrive=1`**：
    丢掉它物理就开始跑，截到的是运动中姿态（实测全图差异 41597→95829px、平均差 13.94→27.78），
    会误判成「这一版改坏了」。
14. **按颜色拆同一层：边界必须沿用原 alpha，两个 mask 严格互补；能整层调 order 就不要拆。**
    拿 `binary_opening/closing` 清颜色 mask 会改动边界像素，`~mask` 补不回原样，接缝两侧各丢一点
    alpha —— 渲染出来是「胳膊上一条拼缝」，用户一眼看到并直接点名。守则：mask 只用来分区着色，
    alpha 一律 `alpha_out = alpha_src`，并 assert `mask.sum() + (~mask).sum() == (alpha_src>0).sum()`。
    决策前先量重叠：实测 `围裙∩手` 只有 268px（可忽略）、`围裙∩袖` 3698px（本来就该被盖）——
    「必须被盖住的部分」占比很小时，整层前移既盖上袖子又保住手，且结构上不可能有拼缝。
15. **像素统计前先清掉页面上的说明文字。** 播放页左下角常有一行白色说明（「…都是真实物理」），
    会被算进「模型有、原图没有」：实测让多件从 71530 虚高到 73533、脚区差异从 2068 虚高到 27887，
    看着像整身错位。统计前把含该文案的 `div/p/span` 设 `display:none`，或把底部裁掉；
    报数字时说明「已隐藏页内文字」。
16. **隔离看某一层用「隐藏其他层」，不要「只留一层」。** 引擎的 view 取 parts 并集，只剩一个 part 时
    会被适配满屏（实测 163×206 的鞋铺满 1280×1280），据此算出的位置/尺寸全是假的。
    做法：`m.parts = m.parts.filter(p => p.id !== 'legwear')`，逐次少一层对比。
17. **z-order 不能从原图的视觉堆叠反推，必须两种排列都渲染再量。** 直觉会告诉你「原图里白袜盖住鞋
    ⇒ `legwear` 该排在 `footwear` 之上」，但 See-through 的层归属是「每个可见像素只归一层」，
    同一层里可能同时装着看起来在上和看起来在下的内容，所以**原画的可见堆叠 ≠ 层的绘制顺序**。
    实测：袜盖鞋 3634px、鞋盖袜 1916px（脚区共同区差异），前者才符合直觉却是错的。
    做法：两种 order 各 build 一次、各截一张同姿态图、按区量差异，取小者；不要靠推理定层级。

18. **合成偏亮是 See-through 层的固有误差，先量出来再动层级。** 拿 17 层 PSD 的 `composite()` 和
    输入原图逐像素比：实测**平均差 24.29、143270px 差异>30，整体偏亮约 25**。原因是它的层是
    「每个可见像素只归一层」，半透明边缘被多层重复计入，叠起来就偏亮。
    症状是「不管怎么调层级/枢轴，颜色都是错的、发白、像蒙了一层」——很容易误判成渲染管线或
    材质问题，其实素材颜色本身就不对。

    **颜色源的致命陷阱：`psd.composite()` 不是原图。** 实测同一套 17 层自身合成与输入原图
    平均差 24.29、143270px >30（整体偏亮约 25）。拿它当颜色源，合并层的鞋区就会显示成白色
    而不是深蓝（实测采样 (600,1050)：层 RGB [254,250,254]，原图 [34,46,90]），视觉上就是
    「鞋面被白袜盖住」。**颜色必须从原图图像文件读**（`Image.open("input/xxx.png")`），
    不能用 `psd.composite()`。

    **但绝不能整张画布无条件替换 —— 会拖出别的部位。** 各层的 alpha 都有溢出（盖到相邻部位上）：
    实测 tail 溢出 14520px x[441,631] y[732,898]（裙摆区）、handwear 5250px（躯干内侧）、
    headwear 6939px（耳区）。无条件换色后，这些溢出块显示的是「原图最终画面」即上层的内容，
    该层一摆动就把别人的身体拖出来 —— 用户判「衣服(胳膊)、耳朵、尾巴跟都有多余身体粘连」。
    正确判据：**本层颜色 ≈ 原图**（差异≤60）才算它自己的内容，才换色；差异大的一律保留本层原色。
    另外 under-paint 过的层（给耳朵洞填头发纹理的 headwear）必须整层跳过，否则填好的头发会被
    原图的耳朵盖回去，形成「耳朵原始图层没清理掉」的重影。
    分区替换后全图差异会从 1.07 回到 3.94，但粘连消失——**优先级是结构正确而非像素最小差**。

    **修法：alpha 保留分层结果，RGB 按「是否本层内容」分区换成原图。**
    ```python
    ref = np.asarray(Image.open("input/原图.png").convert("RGB"), dtype=np.uint8)
    for name, im in out.items():
        a = np.asarray(im.convert("RGBA")).copy()
        if (a[:, :, 3] > 0).sum() == 0: continue
        a[:, :, :3] = ref          # 每层只贡献「这块归我」的形状
        out[name] = Image.fromarray(a, "RGBA")
    ```
    这一条把全图差异从 **43386px / 平均差 14.97 降到 4429px / 1.53**；配上白底后 **5481px / 1.07**，
    脚区 **43px**（原 3778px）、领口 **16px**（原 1754px）。
    验证：改完 PSD 自己的 `composite()` 应与原图逐像素一致（实测角色区平均差 0.03、>30 为 0px）。
    不要再试 alpha-bleed 把边缘浅色换成内部色——实测差异反而升到 19618px，因为原图边缘本来就是浅色抗锯齿。

19. **「黑底上的一圈白毛边」是背景色问题，不是模型问题。** 原图白底、播放器黑底，
    边缘那圈抗锯齿浅色在白底上融进去、在黑底上就显成白边。把播放器 `background` 改成 `#ffffff`
    （或加个白/深切换按钮）就消失了。实测同一模型黑底上被 VLM 判「大量白噪点/锯齿白边」，
    换白底后判「未见白边/白噪点，与原图一致」。改像素去补白边是本末倒置。

20. **用户说「这些东西应该是一个整体」时，优先合并图层而不是调 z-order。** 腿部实测：
    `legwear` 与 `footwear` 两种排列都被否（袜盖鞋→鞋带被吃 3634px；鞋盖袜→脚腕露洞 1916px），
    用户直接裁定「腿 脚 鞋应该视为一个整体图层」。合并成一个 part 后不存在遮挡关系，
    结构上就不可能再出镂空/错位。做法：`alpha` 取两层 over 并集（保留各自抗锯齿），`RGB` 取原图。
    并集若漏像素（实测缺 8212px），补的时候**必须限制在并集附近**——直接撒整个 bbox 会把裙摆
    一起吞进来（实测面积从 53k 涨到 227k）。

21. **按颜色拆出的层必须按连通域再筛一次，否则会把邻近的同类白色吞进来。**
    实测围裙按「白+低饱和」抠出后有 **4 个连通域**：44355px y[582,821] 是真围裙，
    另三块 7353+2752+1953px 落在 y[422,553]，是**衬衫领口的白色荷叶边**。
    它们跟着 `def_Skirt` 摆、又排在 `topwear` 之前，就把领口盖住了（用户：「衣服上有一点小瑕疵」）。
    修法：只保留**最大连通域**，其余归还原层（实测领口差异 1754→16px）。

22. **按连通域「圈出某个部件」这一步，先确认它没把整层连成一块。** 实测 headwear（白色蕾丝头饰
    + 两侧耳朵）在 alpha 上是**一整块连通域**，用 `np.isin(lbl, 与种子连通的块)` 圈耳朵会把整层都算进去：
    挖空 38666px > 层自身 37832px，直接把 headwear 挖没，build 报 `!! 缺 headwear`。
    正解：以部件特征色为种子，只取**种子 N px 半径内**的像素（`binary_dilation(seed, 17x17) & alpha`），
    再 closing 补缺口、小范围 dilation 吃抗锯齿。这样只圈到部件本体 + 绒毛边，不伸到邻近部件。

23. **补色 / under-paint 的「覆盖率阈值」会把整段静默跳过。** 曾写：「若 back hair 在本区覆盖 >30% 才用它补色」，
    而实测 back hair 覆盖 17.6%、front hair 13% → `src=None` → **整段填充根本没执行**，什么都没改，
    而层数和覆盖率都正常，极难发现。症状是「改了但画面一点没变」。
    守则：阈值判空时至少打一行 `!! src=None`；能直接挖空（alpha=0，让下层显示）就不要补色 ——
    耳朵区实测下面本来就有 back hair 6802px + front hair 5055px，挖空就是对的。

24. **给某层补 alpha 时，补块矩形不能竖切进上面的件。** 实测为修「鞋面半透明」把 legs 的 alpha 补成
    `[740:1215, 520:800]`，起点 740 正好切进围裙（围裙 y 到 821）—— legs 带着原图颜色盖到围裙上
    （legs∩apron = 7646px），围裙边缘出现重影/黏连。修法是起点放到所有上层件的下沿之下（改 880）。
    补之前先查「该矩形与每个上层件的 bbox 重叠多少」。

26. **双腿要真分开，走「骨骼关键点 + 像素结构」两段式，不要整块套胶囊。**

    **第一步 DWPose 必须 `det_filename=None`。** 默认的 `yolox_l.onnx` 是照片域检测器，动漫立绘一个人都框不出来，
    表现为 `people` 列表为空 → `out[1]["people"][0]` 直接 IndexError。源码 `wholebody.py`：
    `if self.det is None: det_result = []`（整图当一个人）。改完 18 点全中（conf 1.000）。

    **单次检测只认得对一条腿，要两段互补。** 实测全图段：右腿三点缺失、左腿完整（thigh 172 / calf 144 / ratio 0.84）；
    人物区放大段：右腿完整（187/179/0.96）、左腿踝错（calf 仅 43，ratio 0.23）。**每条腿取自己有效的那一段拼起来**。

    **有效性必须两个判据同时过，只看像素会放过坏点。**
    · 像素：膝、踝落在该件 mask 内（或 3px 内）—— 髋常被裙子盖住，允许不在内
    · 几何：髋→膝→踝单调向下，且 小腿/大腿 ∈ 0.5–2.0（实测那个错锚 ratio 0.23 一看就假，
      但它落在腿区域内，像素判据单独用会判 PASS）

    **胶囊宽度用素材实测，不要套人体比例。** 按耳间距↔14.5cm 标定出腿宽 132px，而这条 Q 版腿实测只有 55–72px，
    132 会横向吃掉另一条腿。做法：在该腿连通域范围内逐行量宽度取中位数。

    **双腿必须分两段处理，因为上段根本是连着的。** 实测逐行：y 774–890 两腿+尾巴连成一整块（行宽 173–187px）；
    y 894 起腿与尾巴分开；y 964 起两腿才分叉（72+72）。所以：
    · 下段（分叉区）→ 按连通域分离，边界完全来自素材
    · 上段（合并区）→ 沿「髋中点 → 膝中点」延长线切，并各留 10px 重叠防摆腿露缝
    · 切缝大部分在裙摆（y≤905）之下，只在 905–964 可见 ~60px，而那段腿根几乎不动

    **三个会静默漏像素的坑，逐个都咬过：**
    ① `find_fork_y` 判的是「逐行几段」，`split_lower` 做的是**二维连通域** —— y_fork 那行虽已是 2 段，
       但相邻像素仍连着，整块还是一块（报「下段没能分出两块」）。切分起点要再往下让 30px。
    ② 上段上限只取到 y_fork，下段从 y_fork+30 开始 → 中间 30px 谁都不管（实测漏 4193px）。上段必须取到下段起点。
    ③ 上段没限 x 范围 → 把尾巴残块（x[520,582] y[880,961] 3694px，See-through 错归给腿）包进左腿，
       bbox 一路延到 520。上段要限在「两髋 ±45px」内。

    **拆完的层要在原脚本里生成，不要读回 PSD 重建。** `l.composite()` 给的是「该层 + 下面所有层」的合成，
    `l.topil()` + `PixelLayer.frompil` 二次写回也有 alpha 损耗 —— 两种都会把合成差从 0.03 推到 4.8–6.8。
    正解：把 mask 存成 `.npy`，在原本生成 PSD 的脚本里读 mask、直接产出 `leg_L/leg_R` 两个层。

    **两条腿的弹簧不能吃同一个输入。** 都绑 `ParamBodyAngleX weight 0.8` 时，刚度再不同也只差一点相位，
    实测像素相关 r=0.897（看着就是一起摆）。给不同输入源（一条吃身体横摆、一条吃头部侧摆，
    两者在 idle 里周期 6.5s / 4.0s 本就不同）+ 拉大刚度差，r 降到 0.821。
    验收：两腿运动量都 >3 且 r < 0.9。

27. **「某层半透明」先查是谁盖住它，不要先抬 alpha。**

    症状：「脖子半透明了」，同时 PSD 里 neck 层 alpha 已是 100% 不透明。
    实测 y=428 一行有三层 alpha=255：
    ```
    neck     RGB (225,166,145) 肤色   order 4   ← 正确答案
    topwear  RGB (187,179,213) 灰紫   order 8   ← 盖在上面
    back hair RGB (46,74,150)          order 0
    ```
    **上衣的 order 高于脖子，把脖子整片盖成了灰紫**。See-through 把「下巴到领口」这段同时归给了 neck 和 topwear，
    而 topwear 那块的 RGB 是它自己的偏亮底色（分区换色时因差异>60 被保留）。
    抬 alpha 完全无效（它本来就不透明）；改这些像素的颜色也不对。**应该把 topwear 在脖子处挖掉。**

    挖的时候也不能整块挖：neck 的 bbox 一直延伸到 y=454，而 y 438–454 那段在原图里是**衣领/领结（深色）**。
    整块挖会把衣领变成肤色。判据：**只在「原图颜色 ≈ neck 自身颜色」处挖**。

    同理，抬 neck 的 alpha 也要用这个判据：neck 3766px 里只有 542px 是「原图确实显示脖子」的地方，
    其余本来就被衣领盖住（是备用内容）。全抬满会把描边变实心暗块。
    排查序：①先量每行有哪几层 alpha=255 → ②看谁 order 更高 → ③比「本层 RGB vs 原图 RGB」定哪层才是该显示的

28. **镜像枢轴 + 同一参数 = 跷跷板；两只耳朵要拆两套弹簧。**

    实测 `def_EarL` pivot=(-18,372)、`def_EarR` pivot=(90,372)，两者都绑 `ParamEarSway`、都 `rotate −20→20`。
    绕镜像枢轴同向旋转 ⇒ 视觉上一只上翘、一只下压，用户叫它「跷跷板」。

    两步都要做：
    · **反号**：`mat(..., flip=True)` 让 ear_R 的 from/to 互换
    · **拆弹簧**：否则两只永远同相位、分不开

    拆了弹簧还得让它们吃**不同输入**，而且共同输入的权重不能大 ——
    实测两耳都带 `ParamAmbientSway weight 0.8` 时，参数相关 r=0.921（看着还是联动）。
    降到 0.15、主力换成头侧摆(4.0s)/身体横摆(6.5s) 后 r=0.797。

    振幅靠 `scale` 补：公式是 `输出 ≈ (x−L)×scale`，weight 只是输入占比。
    把共同输入压掉后振幅会从 ±6 撑到 ±1，用 scale 150→420 补回来。

    **验收看像素层面的相关，不看参数：** 参数 r=0.797 但像素运动相关 **r=−0.076**（几乎不相关），
    且亮度偏移相关 +0.412（正值 = 同向变亮变暗，不是一明一暗）。参数值有相关不代表画面上两只在联动。

29. **「矩形分离」的真因：拿中线当边界。要找前腿在分叉处的真实右边界。**

    实测前腿真实右边界 x≈645–650，而「髋中点→膝中点」中线在 x≈679 ——
    多出来的 30px 就把后腿的一部分划给了前腿（用户：「左边的腿附带了右边的腿的一部分」）。
    做法：在**真分叉行**读 `segs[0][1]`（前腿右边界），向上逐行延伸；
    合并行用「合并块中点 − 5px」近似。

    三个必须排除的干扰：

    · 上/下段之间不能漏行：上段取到 fork_y−1、下段从 fork_y+2 起 ⇒ y=989/990 两行无人区，
      渲染出来是一条**水平白线**（用户：「双腿袜部出现水平白线切割/错位」）。下段直接从 fork_y 起。

    后腿在重叠带里的内容要用**它自己的像素横向填实**，不要留着前腿的像素 —— 否则摆腿时拖出前腿的边。

30. **numpy 广播能静默吃掉你所有的边界计算——切分前必须先做「左端/右端一致性」自检。**

    连改 12 版都没修对腿的根因不是参数，是这一行：
    ```python
    xx = np.arange(W)[None, :]      # (1, W)
    split_x                          # (H,)
    m_front = upper & (xx <= split_x)   # ← 广播成 (1,W) vs (1,H)
    ```
    两边按**最后一维**对齐，于是变成「第 x 列 比 split_x[x]」——拿第 x 行的边界判第 x 列的像素，
    **行列完全错位**。而且不报错，只是边界永远不生效。

    **症状特征：**调参完全无反应，某个方向被钉在一个固定值上（这里前腿右端恒为 650）。
    **发现方式：**在赋值后立刻打一行自检，把「设计值」与「实际结果」并排比：
    ```python
    for _y in (800, 820, 900):
        print("y=%d split_x=%d m_front右端=%s" % (_y, split_x[_y], np.nonzero(m_front[_y])[0].max()))
    ```
    实测输出 `split_x=675  m_front右端=650` —— 两者矛盾就说明运算没按预期广播。
    **修法：**`split_x[:, None]` → (H,1)，再与 (1,W) 广播成 (H,W)。
    推到同类：只要把「一维逐行数组」和「二维坐标网格」混用，就必须写成 `arr[:, None]`。

37. **羽化两个坑：一半被裁掉、两层都羽化会透底。**

    接缝变半透明直接透底。
    **正解：只羽化前腿，后腿保持 alpha=1 兜底** —— 叠加恒为 1，而前腿边缘仍是柔的。

    另：`m_front` 不能跟着向右扩 FEATHER（会多拿后腿内容），实测腿区差异 404→532px。

39. **alpha 羽化 = 两层颜色混合 = 视觉上融合成一条。想“分开”就不能羽化。**

    为了消除硬边，我把前腿右边缘做了 6px alpha 渐变。结果叠合公式

    两层确实是独立的 part、独立 deformer、各自 param，但像素掺混后眼睛看到的就是一条。
    → **接缝靠重叠带宽解决，不靠 alpha 羽化**。

    **另一个陷阱：同源输入会把两腿变成同步摆。**

    实测最终状态（v61）：
    ```

    腿L ±0.98 / 腿R ±1.31（后腿幅度只有前腿 60%）
    分界缝 +4~6px（原图基准）
    静态腿区 401px（历史最低）
    ```

    **验收口径要一起看两个数：**
    · 参数相关 < 0.85 → 两腿真的在分头动（不是同步）
    · 分界缝宽度 ≈ 原图 → 没有把间隙撑开
    只看其中一个都会调错方向（看缝→改同源→融合；看相关→改异源→撑缝）。

47. **自动拆腿：`FRONT_W` 用「分叉区左段宽度中位数」，不要用「单段行」的宽度。**

    单段行往往只剩鞋底那几行（实测只有 3 行），算出 37px 而真实腿宽 76px —— 底部两鞋靠在一起时
    就会整块判给一条腿。另外**单段行要分两种情况**：明显偏左/偏右 ⇒ 只是其中一条腿存在，整块归它；
    横跨中线且够宽 ⇒ 两腿连成一片，按 `FRONT_W` 切。漏掉这个判断会把「只有右腿的那几行」划给左腿。

    完整判定流程（分叉点、有无合并区、描边外侧边界、抗锯齿 alpha 保留）见
    `references/layer-splitting-rules.md` §7。

25. **两种互斥排列都被用户否掉时，问题在素材粒度，不在层级。** 会出现这种循环：袜盖鞋被否
    （「双脚盖过了鞋子」）、改成鞋盖袜又被否（「鞋到了前面、脚腕镂空」）——两种都错说明**层里缺东西**。
    这时不要再翻第三种排列：把两种的区差异数字摆出来（1916 / 3634）、把缺失像素的**原图颜色**查出来
    （实测那 1578px 原图是 rgb(74,73,76) 深灰描边，See-through 没单独拆出来），然后给两条结构路线
    让用户定：①重抠该小块的语义份层（范围明确、可用 PSD 合成差异验证）；②换更细的拆层粒度。
    试过的挖补全部记成死路（双向互挖把 PSD 合成搞差、单侧挖 footwear 露黑底），不要当方法复用。

26. **任何层的 alpha 里有成片的 1–254，渲染出来就是一层雾 —— 它会把下面的层透上来。**

    主体区内的半透明像素一律抬满 255；**只抬主体、不外扩**（外扩会取到背景色，渲染成白边）。
    ```python
    a = np.asarray(out[name])[:, :, 3]

    ```

    而层数、覆盖率、bbox 全都正常，缩略图上看不出来，只有贴在皮肤这种大面积平色区上才显眼。

27. **对称件的两个 deformer 绕镜像枢轴、绑同一个参数的同向 `from/to`，屏幕上必然一上一下。**
    左耳枢轴在左边、右耳枢轴在右边，两者都 `rotate -20..+20` 吃同一个 `ParamEarSway`：
    对左耳是绕左端转、对右耳是绕右端转，同样 +20° 就是「一个上翘一个下压」。再只配一个弹簧，
    两只永远同相位，永远分不开。
    要各自独立：**拆成 L/R 两个参数 + 两个独立 `physics`**（给不同 `stiffness`/`damping` 让相位错开）；
    只要对称外张就把一侧 binding 反向（`from:20, to:-20`）。
    判定信号是用户说「像一个整体而不是分体」「像跷跷板」——这两句指的都是「两只共享同一个参数」。

28. **单连通域的肢体、又不许补画时，第三条路是「同一 part 内部用 warp 网格分左右」。**
    不拆 part，给该件一个较密的 warp 网格，左半列绑 `LegL`、右半列绑 `LegR`。因为是同一个 part
    的网格形变，不存在两个独立矩形相对错位，结构上不可能露缝；代价是只有网格级形变、没有各自独立枢轴。
    它比补画省事（不破坏原画质感）、比几何硬切安全（用户已明确否过几何切）。
    ⚠️ **本机尚未实测**，动手前先自检三条：①打印每列的角色像素数，中间列接近 0 才说明两腿在网格里
    真占到不同列；②网格密度至少覆盖到两踝间距的一半；③绑完用 `scripts/measure_underlayer_leak.py`
    对中间缝做一次露底统计，摆动帧不得高于静止帧。三条中有一条不过，就回到「整块小幅摆 + 明说上限」。

29. **「看着缺一块」先回原图量同一处；原图本来就这样就不是 bug。** 实测左鞋后帮「缺一块」，
    该区原图白色(袜) 1616px > 深蓝(鞋) 1381px —— 白袜本来就压在鞋后帮上，模型层级是对的。
    判法：隐藏上层后若该件立刻变完整 → 是被上层盖住；再看原图同位置颜色占比决定是素材特征还是真错。
    两种可能都报给用户选，不要自己「修」掉原画的设计。
    三方对比（原图 / PSD 自身合成 / 模型渲染，同一原生尺寸）能一次定位是谁的错：
    PSD 对而模型错 = 渲染管线；PSD 就错 = 素材或层序（实测脚区 PSD↔原图 4007px、模型↔PSD 24651px）。
    另：`crop_to_alpha(soft=8)` 会让 part bbox 每边大 8px，纹理与 mesh 一起偏移，**渲染不错位**，
    不要拿 ±8px 的 bbox 差当 bug 追；要看渲染后的 bbox 是否与原图一致。

## 用户一定会问的三个入口（先讲真相，再改）

1. **撤销**：功能一直在 `store.undo/redo`（文档层命令栈），只是按钮初态灰（没有历史）——用户很容易
   判成「没有撤销」。上游**没有快捷键**，按钮在右栏最顶部还要滚动才看得到。
   补法：在 `App.tsx` 挂一个 window `keydown`，Ctrl+Z / Ctrl+Shift+Z / Ctrl+Y；**焦点在
   input/textarea/contenteditable 时 return**，把撤销让给浏览器原生实现（否则改数值框时行为错乱）。
   按钮文案写成「撤销 (Ctrl+Z)」+ `title` 说明当前能不能撤。
2. **导入**：原来只有「导入图层组」，`accept="image/png,.psd" multiple`，且 `parseLayerRoles` 按**文件名**
   卡 role（face、eye_L、eye_R、mouth…），乱命名的单张图、jpg、随便一张 png 全部被拒。
   所以「没有导入图片的地方」是真实缺口，不是用户没找到。
3. **自动识别**：见上表。切层要 landmarks，没有模型兜底。

## 加「导入单张图片（整层）」的配方（已实测跑通）

```tsx
// Inspector.tsx
const decoded = await decodeImageFile(file, { premultiplyAlpha: "none", imageOrientation: "none" });
store.addPart();                                  // 新建部件并自动选中
const id = useEditorStore.getState().selectedPartId!;
const { width: iw, height: ih } = decoded.bitmap;
const k = Math.min(1, 900 / ih, 1100 / iw);       // 画布高 1608（1100 宽图层画布）
runCommand(new SetPartWidth(id, Math.round(iw * k)));
runCommand(new SetPartHeight(id, Math.round(ih * k)));
setPartTexture(id, decoded);                      // atlas 侧表接管位图所有权
```

坑：
- 失败路径必须 `decoded.bitmap.close()`（atlas 侧表只接管成功的那份，否则泄漏）。
- 三条 `runCommand` = 三条 undo 步，可接受；不要为了「一步撤销」去拼自定义命令。
- UI 文案里**明写**「整张作为一个部件，不会眨眼张嘴」，否则下一步必然被问「为什么不动」。

## 自动切层的真实流程

1. `pnpm --filter @ikijs/mcp build`
2. `viewIllustrationGrid({imagePath, outputPath, zoom, step, crop})` → 出**1100 宽**画布上的带网格读取图
   （zoom 1..8 整数，step ≥5；`crop{x,y,w,h}` 用画布坐标）
3. 读网格写 landmarks（模板见 `templates/landmarks-min.json`）
4. `cutLayersFromIllustration({imagePath, landmarks, outputDir})`
5. `autoRigFromLayers({layers:[{path}…], outputPath})` → `.iki`
   ⚠️ 层表**不要手写固定数组**：cut 的层集随 landmark 变（补了 `nose` 就多一层），
   手写列表会把它静默丢掉 —— 症状是模型 `parts` 比 cut 少一个、`turn` 缺失、转头死掉，
   而 rig 照样返回 `ok:true`。用 cut 返回的 `layers[].role` 或对目录 readdir 过滤来生成层表。

**必填的 landmark（少一个就直接 REFUSED，报错会一个个点出来）**

| 键 | 内容 |
|---|---|
| `samples.hair.base[]` / `samples.skin.base[]` | 平色块上的点，各 ≥1 |
| `eyes.L/R` 的 `box` + `iris{cx,cy,rx,ry}` | 整只眼含睫毛的框；虹膜椭圆 |
| `mouth` 的 `box` + `cornerL` + `cornerR` | 只给 box 报 `landmarks.mouth.cornerL is missing` |
| `frontHair[]` | 刘海+贴脸鬓发的闭合多边形，≥3 点 |
| `skull[]` | 头骨轮廓（被头发遮住的皮肤也算进去），≥3 点 |
| `shellLower[]` | 后发下沿，**x 严格递增**，≥2 点 |
| `skinSeeds[]` | 脸上的点，≥1（脸颊最稳） |
| `bodySeeds[]` | 脖子/胸前的点，≥1 |
| `neckTopY` | 数字：下巴后方脖子的上沿 |

可省：`brows`、`nose`、`sideHair`、`backgroundSeeds`、`paintSeeds`、`bodyOnly`、`customParts`。
`sideHair` 的格式是 `{L?: Point[], R?: Point[]}` —— **纯点数组**；带 `id/side/tie/line/below` 的对象
是 `customParts` 的 `IllustrationSideCut`，塞进 `sideHair` 会被拒
`must be an array of [x, y] points`。
`nose` 名义上可省（cut 照过，只写一条 `measure.warnings`），但**省了转头就废**：
rig 出来的模型没有 `turn` 数据，`ParamAngleX` 写 30 回读只有 0.2–1.4，等于没转。
Q 版脸的鼻子就是一个高光点，框住它只要几十像素，没有理由省。完整骨架见
`templates/landmarks-min.json`；逐点标法见 `references/landmark-authoring.md`，探针脚本 `scripts/probe_landmarks.py`。

硬规则：
- **`L` = 角色的左眼 = 观众看到的右边。** 搞反会被当场拒绝：
  `... L is the character's left eye, on the viewer's right, so the two look swapped`。
- `samples.hair/skin` 必须落在**平色块**上；取点落到对方类别的漆上，整张图的头发与脸会互换。
  描边、阴影线、纯黑处都不能当 `skin.shadow`（实测 rgb≈(13,4,2) 的是轮廓线）。
- `bodySeeds` 落在**蓝色衣服**上会被读成头发而 FAIL —— 改用白围裙那类非蓝漆，或给一个 `bodyOnly`
  多边形把衣服的蓝划给身体。
- 虹膜估小了看 `iris.L/R` 的 hint：它直接报「the disc found spans x 537..598 (rx about 31.0)」，
  照抄这个范围，不要自己估。
- `outputDir` 必须在 cwd 之下且已存在；同一目录可复用，同名文件覆盖。

**怎么读 checks（读错这一条会把通过判成失败）**

`CutCheck` 是 `{id, level, pass, value, limit, hint}`：`level` 只是**严重级别**（`"fail"` / `"warn"`），
**判定在 `pass`**。`mouth`、`stack` 这类 check 天生 `level:"fail"`，只要 `pass:true` 就是过了。
打印时先打 `pass ? "PASS" : "FAIL"` 再打 level；只看 level 会以为满屏失败、白改两轮坐标。

`cutLayersFromIllustration` 返回
`{ok, outputDir, canvas, layers[{role,file}], customParts, previews{labels,landmarks}, checks[], measure, passed}`
—— 没有 `files` / `lines`，照 `console.log(r.files.length)` 写会 undefined 崩。

降 FAIL 的顺序：先修 `pass:false` 且 `level:"fail"` 的（实测卡得住的只有 `seeds`、`opening.*`），
`passed:true` 之后仍会剩 warn（`iris.*`、`fills.face.forehead`、`frontHairWidth`、`pockets`），
每条都有肉眼后果，按下面「固有上限」讲给用户。正常 2–3 轮就 `passed:true`，不要想一轮标完。

现成调用脚本范式：`node cut.mjs <outDir>` 里 `import {cutLayersFromIllustration} from "file:///D:/…/packages/mcp/dist/index.mjs"`
——**用 file:/// 绝对路径 import**，相对路径在别的工程目录下解析不到。

## 验收：先让它在播放器里动起来

`cut → autoRig` 只代表文件写出来了，**必须自己加载一次并逐项回读参数**，否则「检查都过了」可能是假的。

```bash
cp model.iki refs/iki/examples/player/public/    # public/ 没有就建
curl -s --noproxy '*' -o /dev/null -w "%{http_code}\n" http://127.0.0.1:5200/model.iki
```

```js
// browser_exec(local=True)，页面 http://127.0.0.1:5200/
await fetch('/model.iki').then(r=>r.text()).then(t=>window.iki.load(t))    // load 吃 JSON 文本，不吃 URL
// 待机动画每帧会把参数写回去：用 16ms 定时器持续重设，比 stopIdle() 可靠
window.__h = setInterval(() => { window.iki.set('ParamMouthOpenY', 0.9); }, 16)
window.iki.get('ParamMouthOpenY')                                          // 回读，才算真设上
```

**让用户打开页面看到的就是它**（不做这步 = 交付失败）

播放器默认 `void load(sampleModel)`，也就是内置的棕发示例。只在自己会话里 load 一次，用户刷新看到的
仍然是那只示例，会直接回「没有看到你做的大肥鱼」。改 `examples/player/src/main.ts` 尾部：

```ts
// 无 ?model= 时优先加载工程自带的模型，失败才回退内置示例
const res = await fetch("/model03.iki", { cache: "no-store" });
if (!res.ok) throw new Error(`HTTP ${res.status}`);
await load(await res.text());          // load 吃 JSON 文本，不吃 URL
```

`?model=<url>` 分支同样要先 fetch 再 `load(text)`。改完 `explorer.exe "http://127.0.0.1:5200/"`,
再用**无参数** URL 截一张图确认画面是蓝发（不是棕发示例）—— 这才是「用户能看到」的证据。

坑：
- `window.iki.load('/model.iki')` 传 URL 会走 `JSON.parse(url)` → 页面底部报「加载失败 / invalid JSON」，
  画面仍是内置示例模型（棕发短发），极易误判成「切层失败」。必须 `fetch(...).then(r=>r.text())`。
- 便捷函数 `mouth()` 实测回读一直是 0；口型直接用 `set('ParamMouthOpenY', v)`。
  `head(x,y)` → `ParamAngleX/Y`、`set('ParamEyeLOpen',0)`/`ParamEyeROpen` 闭眼都有效。
- `capture_screenshot()` 每次返回**同一个路径**，连拍会互相覆盖 —— 拍完立刻复制成不同文件名，
  最后再拼成一张对比图。只留最后一张会得出「三个姿态一模一样」的错误结论。
- **判画质前必须先确认 `canvas.width` 的真像素尺寸**（本轮最贵的一个坑）：标签页在后台时
  `requestAnimationFrame` 被节流，引擎里那段 resize（`player.ts`：`canvas.clientWidth * dpr`）根本
  没跑，`canvas.width` 停在 HTML 默认 **300×150**，全靠 CSS 拉满屏。这时截的图是 300×150 放大，
  1 px 的层缝被放大成肉眼 4 px，干净画面也会被看成糊/撕裂。配方：
  ```js
  cdp("Page.bringToFront"); cdp("Emulation.setFocusEmulationEnabled", enabled=True)
  cdp("Emulation.setDeviceMetricsOverride", width=1000, height=1000, deviceScaleFactor=1, mobile=False)
  // 之后 js("document.querySelector('canvas').width") 必须是 1000，不是 300，否则还不能截图
  ```
- `stopIdle()` 会把渲染停在最后一帧（画布尺寸也停在旧值），拿它当「冻结姿势」会截到旧画面；
  保持参数用上面的 `setInterval` 重设法，不要停循环。
- 给用户的图：默认 / 闭眼 / 张嘴 / 转头四格拼一张，标签写在格子外面（不压在图里）。
- **转头是否生效用像素差分判，不要问 VLM。** VLM 看四格拼图会答「没转头」（它读不出一两像素的位移），
  而实测同一组图头部区域均值差 9.9 / 10.7、各 6.9–7.2 万像素差异 —— 转是真在转，只是 Q 版看不明显。
  判法：同一画布尺寸截「默认」与「±30」三张，`np.abs(A-B)` 取上半张算 `mean` 与 `>10` 的像素数；
  均值差 <2 才是真没转（deformer 没接上，或 landmark 缺 `nose`）。
- **判「某个部件动没动」用分区运动量，不要看缩略拼图。** 连拍 40 帧（CDP clip 到 canvas，间隔约 0.12s），
  逐帧与首帧求灰度差、按区域（头部 / 后发 / 尾巴区 / 裙腿）取均值。同一组帧里，缩略图上会得到
  「没动」的印象，分区数字可能差 4 倍；反过来均值 <0.5 的区域就是真没动，回去查那一层有没有独立物理，
  别靠调旋钮。直接跑 `scripts/measure_motion.py <帧目录或glob> --heat heat.png --gif out.gif`；
  形状判断再裁到该部件放大 4 倍交给 VLM。

**这条管线的固有上限（要主动说，不是 bug）**
- 没有 lip set（口腔+牙+舌素材）时，张嘴 = 把原画嘴线**纵向拉大**，开度 0.9 会有锯齿感。
  要真口腔得另给 `mouthKeyed` + `mouthInterior`。
- `frontHairWidth > 1`（刘海比脸宽）→ 转头被 clamp 到三成以下（实测 2.65 时 `ParamAngleX` 写 30 只出来 8.6；
  收到 0.82 参数才真正写得进去）。但**收窄只解开 clamp，不等于看得出侧脸**：Q 版头大脖短，
  ±30 时头部区域像素差只有 ~10（6.9–7.2 万像素），肉眼仍是正面。收窄的代价是两侧长发归进后发层。
  → 对 Q 版只承诺「轻微摆头」；要真侧脸得换半身像模板。
- `fills.face.forehead` 偏高 = 刘海下的皮肤是**补出来的**，极端转角会看出补色。
- **层缝（最容易被用户抓的一条）**：单图切层的每层是**像素硬切、互不重叠**，手工 Live2D 那种「每层
  外扩 2–4 px 互盖」不存在，所以部件一动就露底。**补边（alpha 外扩）能把它压到 0.0x%**，
  旋钮、实测数字、什么改动反而更差、以及「白描边外多一圈杂色」的修法，见
  `references/layer-gap-quality.md`；量化脚本 `scripts/measure_gaps.py`（洋红背景 + 逐像素统计露底面积）。
- **缺内容（补边也救不了的）**：口腔、侧脸内耳、被头发完全遮住的皮肤，单图切层里根本不存在。
  正路是先用 See-through 拆成带部分补画的 17–23 层 PSD（部署、耗时、显存、保真度实测见
  `references/see-through-deployment.md`），再直接丢现成消费端自动绑定（`references/psd-consumer-tools.md`），
  而不是自己从零写槽位映射与绑定。

## 关键坑

- **不要让 VLM 打 landmark 坐标，用像素扫描定框再让 VLM 只做复核。** 同一张嘴三次读数互相矛盾，
  其中一次给出的「嘴框」像素统计是 90% 白/肤色 —— 完全是空白处。做法：按颜色分类做横向/纵向游程扫描
  （`scripts/probe_landmarks.py`），在脸的外接框内找 `DARK→WHITE→BLU` 夹层定眼框、`BLU` 游程定虹膜，
  再对候选框算 white/blue/skin 占比做接受或否决。细节见 `references/landmark-authoring.md`。
- **颜色阈值找五官在「包围式配色」里必错**：蓝发把脸围住时，「找蓝色团块=虹膜」命中整片头发，
  「找白色=眼白」命中围裙/头饰和浅肤色（浅肤色 `sat<30` 同时算 white）。像素法必须在脸的外接框内、
  先把肤色团块定位出来再往下找。
- **改含 `\n` 的 Python 脚本用 `write_file`/`patch`，不要用 bash heredoc。** heredoc 里 `\\n` 被 shell 吃掉变成真换行，字符串断裂 → `SyntaxError: unterminated string literal`，而且改的是生成器本体，一崩就是整批不出图（实测一个 60 秒的批量任务白跑）。提示词脚本反复改时尤其容易踩。
- **隐藏的 file input 点不动**：用 CDP `DOM.setFileInputFiles(nodeId, files=[绝对路径])` 直接喂文件，
  然后读部件面板的 width/height 输入值 + 截图，才算证明导入真的落地。
- **改参数表后加载报 `duplicate parameter id "ParamX"`**：refactor 时同一 id 留了两份（新增一条、旧的没删）。
  重跑前 `grep -c '"id": "ParamX"' build_*.py`，必须等于 1。
- 上游 cut 只有 Node 侧实现（sharp）。要「网页里点一下就切」必须起本地服务包一层，
  前端只做上传与装载，别在浏览器里重写切层。

## 交付口径

- **上游交付物一律按「标准命名 PSD」设计**：用户的目标是美工画图、机器绑定，所以每一环都要能直接吃
  PSD（`face / eyewhite / irides / eyelash / eyebrow / mouth_open / mouth_close / front hair / back hair…`）。
  现成能直接吃 PSD（含 See-through 输出）并自动绑定的工具、完整层名规约与实测数字见
  `references/psd-consumer-tools.md`。别把「先把 PSD 转成自家格式」当默认步骤。
- 用户要「说明书」时：以**官方 README + 仓库源码**为唯一依据，逐条标出处（哪一节 / 哪个文件 / 哪行参数），
  本机实测与官方说法**分两栏写**，官方吹的和实测不符的地方必须点名（例：官方写 fully inpainted，
  实测只补到 36–54%）；不要把通用教程或印象当依据。
- 改编辑器只做**加法**（新按钮、新快捷键），不碰既有导入/绑定路径——**回归比缺功能严重**。
- 交付生成图时**同一条消息里写明用的模型与路线**（例：`SDXL WAI-Illustrious + OpenPose 骨架` /
  `Qwen-Image-2.1 参考编辑`）+ 关键参数。用户会按产出特征反推模型（「这是用的 h3 吧」），
  不写明就会把问题归到错的模型上，白耗一轮。
- **用户逐轮验收视觉质量时，要的是「改完的成品 + 证据」，不是选项菜单。** 他说「直接给我修改完的结果 让我来确认」，
  就是不许把「选 A 还是 B」丢回去：先改到当前工具能做的最好，附 40 帧分区运动量 / 热图 / 帧对比，
  再用一句话交代「哪几项这工具做不到、为什么」。下一轮他会继续逐部位点名，照单改即可。
- **逐部位迭代时一轮只动他点名的那一处，并主动交代这一改的代价。** 用户会按部位逐个验收（头发好了 →
  再看腿脚），每一轮都在上一条已认可的基础上改。所以：不要顺手动其他部位（一动就把他刚认可的项拖回风险）；
  改完先拿该部位的数字证据贴上去（运动量 / 相关性 / 露底像素数），再一句话说清这一改牺牲了什么
  （例：「呆毛和侧发不再能独立弹动」「右鞋相关性偏低是因为框里含裙摆像素」）。他对慢但准的迭代明确认可，
  对「一次改十处然后宣称都好」不买账。
- **卡在视觉判断上时，出「同框同倍」的成对局部图 + 编号问题让用户用肉眼判，不要自己反复猜。**
  用户的原话是「你不确定的地方详细告诉我 我用肉眼给你看给你答案」。做法：同一 `box`、同一 `scale`
  裁原图与模型，左右并排、标签写在图外，配 3–5 条具体到部位的问句（「图① 胳膊还在围裙前面吗」
  「图③ 鞋在袜子上面了吗」）。这比再跑十轮自动比对快，也避免把猜测当结论。
- **测运动的帧不是交付的动画。** 为了让数字可读，会用 16ms `setInterval` 把 `pAngleX` 推到 ±0.45、
  `pBody` 推到 ±0.22 持续驱动；那一版看着像抽搐，用户会直接回「动作极其夸张」。量完立刻把驱动全撤、
  姿态参数归零，**另拍一遍纯 idle 作为交付片**。两段素材分开命名（`seq_*/measure` vs `idle_full`），
  数字给前者、动图只给后者。
- **调参工具不是播放器。** Anime2.5DRig 页面只能拖滑杆看，没有「播放成品」这一形态；把它的地址当
  「效果」发过去，用户会说「打开的是一个日语网页，根本没看到播放效果」。绑定用哪个工具是一回事，
  交付时必须另起一个**打开就在播**的页面：把连拍帧合成 GIF，用
  `python -m http.server <port> --bind 127.0.0.1` 起本地 http 给地址（`file://` 页在默认浏览器里常不可靠）。
  同时用一张表说清每个端口是什么（调参工具 / Iki 播放器 / 播放页）—— 用户会同时开着好几个标签，不说明必被搞混。
- 汇报时把「现在能做什么 / 还差什么」分开写；不能全自动就直说，并给两条现实路线：
  ①分层 PSD/命名 PNG（现成，秒级出全套绑定）②agent 标点切单张图（一张几分钟，我做、用户验收）。
- 交模型必须同时给：`.iki` 路径、层目录、四格效果图、「能动什么」的参数清单（眨眼 / 张嘴 / 转头 /
  视线 / 呼吸 / 头发物理）、以及上面四条固有限制。只给文件不说上限，下一轮必被问「为什么动得怪」。
- **默认表演要照原图的叙事来，不能用通用笑脸开局。** 一张图本身就在讲一件事（偷吃被抓包、边嚼边嫌弃、累了趴桌），
  演示与默认参数必须复现那个语义，不能因为「可爱」就套随机表情 / 随机口型预设。
  做法：先写一句话「她正在干什么 + 什么情绪」，再翻成具体参数（例：拒绝 → 半眯眼 + 嘴角下撑 + 小幅咀嚼循环 + 关掉随机表情预设）；
  录之前先自检一次，别把默认姿态当成无关参数。用户会按原图设定逐条对账，跑偏会被直接判成「默认动作不对」。
