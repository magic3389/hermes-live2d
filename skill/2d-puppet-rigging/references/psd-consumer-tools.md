# PSD → 会动的模型：现成消费端与美工交付规范

## 为什么这条比自动切层重要

用户的方向是「**美工画图、机器绑定**」：只要上游交付物是标准命名的分层 PSD，多少美工都能并行产出，
绑定这一环交给工具。所以工具链的每一环都要**直接吃 PSD**，不要在中间自造格式——多一道转换，
就多一批美工进不来。

PSD 有两个来源，消费端应该都能吃：

1. **美工手画的分层 PSD**（Photoshop 导出，层名按下面的规约）
2. **See-through 自动拆的 PSD**（见 `references/see-through-deployment.md`）

## Anime2.5DRig 实操（已用 See-through 的 17 层 PSD 实测通过）

```bash
git clone --depth 1 https://github.com/852wa/Anime2.5DRig.git
cd Anime2.5DRig && python -m http.server 8010      # 纯前端，python 自带 server 足够
# 打开 http://127.0.0.1:8010/index.html ，把 PSD 拖进去（或走「PSDを開く」的文件选择）
```

无头环境下喂文件（已验证最稳的一条）：页面只有一个 `input#fileInput`（`accept=".psd,.json"`），
用 CDP 直接灌绝对路径，比 Blob/DataTransfer 少一层出错点：

```python
root = cdp("DOM.getDocument", depth=2)["root"]["nodeId"]
node = cdp("DOM.querySelector", nodeId=root, selector="#fileInput")["nodeId"]
backend = cdp("DOM.describeNode", nodeId=node)["node"]["backendNodeId"]
cdp("DOM.setFileInputFiles", files=[r"D:\...\xxx.psd"], backendNodeId=backend)
```

40MB 的 PSD 解析约 3–30 秒；判完成看页面上「パーツ・アンカーを生成中…」这行是否消失，
不要用固定 sleep。

加载后它会自己打印诊断，**先读诊断再谈效果**：

```
24パーツ / 揺れもの12本を自動リグ / 1280 × 1280px / ノイズ除去: 17/17レイヤー
```

（实测两张同源 17 层 PSD：都是 24 个部件，摇摆件 **12 根或 15 根**——差距来自层内容：
带独立 `tail` 层的那张多出「尻尾 · 揺れ3」（尾巴 3 根），17 层全部做了连通域去噪。
所以摇摆件数本身就是「拆分带不带尾巴」的信号；明显偏少时先查是不是有部件没被识别，
别急着调参数。）

它自动做的事（不用动手，但要知道它做了才能解释效果）：

- `mouth` → `mouth_open` 自动改名；`hair` 按绘制顺序判前发/后发
- **左右眼 / 眉 / 睫毛 / 闭眼按连通域质心自动分离**
- 眼皮位置、虹膜中心、嘴、脖子枢轴的**锚点自动检测**（可在「アンカー編集」拖修正）
- 发束自动检测（毛尖轮廓峰值，每层最多 6 束）+ 双弹簧物理（根硬梢软）
- 按层深度分配伪 3D 摇头（视差 + 剪切）、呼吸、胸部摇动
- **闭眼 / 闭口差分缺失时自动生成**：拿仓库根 `eye_close.psd` / `mouth_close.psd`（或内置数据）
  按锚点缩放贴合、颜色对齐睫毛/嘴色。**所以美工可以不画闭眼闭口**，手画质量更好但不是必须

## 层名规约（要给美工的就是这张表）

名称自动规范化：`のコピー` / `copy` / 全角 / 大小写 / `_` `-` 空格 视为同一层。

| 层名 | 别名 | 内容 | 必须 |
|---|---|---|---|
| `face` | 顔、輪郭 | 脸底 | **◎ 唯一必需** |
| `eyewhite` | 白目 | 眼白（左右可合成一层） | ○ |
| `irides` | 瞳、黒目、iris | 虹膜 | ○ |
| `eyelash` | まつ毛、アイライン | 睫毛/眼线（开眼） | ○ |
| `eye_close` / `eye_close2` | 閉じ目 | 闭眼差分 / 长闭眼 | ○（可自动生成） |
| `eyebrow` | 眉 | 眉 | ○ |
| `mouth_open` | 口、開き口、mouth | 开口 | ○（`mouth` 会自动改名） |
| `mouth_close` | 閉じ口 | 闭口 | ○（可自动生成） |
| `nose` `ears` `earwear` `eyewear` `facedetail` | 鼻 / 耳 / ピアス / メガネ / 頬 | 零碎件 | 可选 |
| `neck` `neckwear` `topwear` `handwear` `bottomwear` `legwear` `footwear` | 首 / チョーカー / 服 / 腕 / スカート / 脚 / 靴 | 身体 | 可选 |
| `front hair` `side hair` `ahoge` `back hair` `hair` | 前髪 / 横髪 / アホ毛 / 後ろ髪 / bangs | 头发 | 可选（有专门物理） |
| `headwear` `tail` `wings` | 帽子 / 尻尾 / 羽 | 配件 | 可选（`tail` 会被识别成「尻尾 · 揺れN」，但只是**被动跟随**，idle 下几乎不动，见下节实测） |

- **头发分多束就写 `front hair_1`、`front hair_2`**，每层独立物理；束数按层宽自动定。
- 规约外的层名也被读进来（按位置判头/身，只做跟随），在诊断里显示为未分类——不是报错。
- 图层组（文件夹）里的图像层同样吃，隐藏的层/组会跳过。

## 三个会毁掉效果的限制

1. **`neck` + `topwear` 前后关系会破**（官方明确写）：See-through 直接输出的脖子与躯干，动起来接缝
   容易崩。**把脖子合进上装做成一体型**（去掉 `neck` 层、`topwear` 含到脖子）更稳。
2. **画布要正方形**，官方验证区间 768×768 ~ 2048×2048；PSD 只收 **RGB / 8bit、≤128MB**。
3. **真实感/非二次元风格会拆错**：See-through 只按动漫与 VTuber 立绘训练。

## 验收：别目测，量「内部洞」

单图切层时代的撕裂指标是「露底率」；到 PSD+自动绑定时用**角色内部空洞**更直接：

```python
m = character_mask(img)                       # 把深色棋盘格背景排除掉
holes = ndimage.binary_fill_holes(m) & ~m     # 被角色轮廓围住却透明的区域
```

实测这张 Q 版（17 层 PSD 自动绑定）：正面 2.11% / 转头 X=1 2.11% / 转头 Y=1 2.05% / 闭眼 1.96%。
**转头前后几乎不变 = 没有新增撕裂**，剩下的是角色设计本身的镂空（长发与身体的月牙缝）。
判据就写「转头前后洞率变化」，不要写一个绝对阈值。

## 无头截图：WebGL canvas 读不出来

`canvas.getContext('2d')` 在这些渲染器上返回 null；`canvas.toDataURL()` 在没开
`preserveDrawingBuffer` 时会返回**全透明**的图（实测 1280×1280 只有 37KB、alpha 全 0，五张不同姿态
字节数完全一样）。别据此判定「模型没渲染」。

正解：**CDP 定点截图**，clip 到 canvas 的 `getBoundingClientRect()`：

```python
cdp('Page.captureScreenshot', format='png',
    clip={'x': rect[0], 'y': rect[1], 'width': rect[2], 'height': rect[3], 'scale': 1})
```

四张姿态图字节数各不相同（428542 / 428594 / 431292 / 420004）才说明真的换了画面。
注意截图含棋盘格 CSS 背景，判角色时按背景色（深色主题下是两种近黑灰）排除。

## 导出录像：三个实测坑（Anime2.5DRig v2.0）

导出面板四个选项：背景（transparent / green / dark）、时长（3–60s）、帧率（30/60）、
格式（vp9 / vp8 / webm / mp4）。**别信「透過 WebM」**：

1. **transparent 实际导出没有 alpha**：ffprobe 显示 `pix_fmt=yuv420p`（不是 yuva420p），透明区变纯黑，
   深蓝头发/裙子直接融进黑底。根因是 Chrome 的 `MediaRecorder` 不支持 alpha 通道，不是配置错。
   → **要交付就用 `green`（绿幕）**，后续用 colorkey 抠，或直接当背景看。
2. **选 `video/mp4` 出来的仍是 `vp9 in mp4`**（ffprobe 会告诉你 `codec_name=vp9`），兼容性差。
   交付前必须转一次：`ffmpeg -i in.mp4 -c:v libx264 -pix_fmt yuv420p -crf 21 -movflags +faststart out.mp4`。
3. **WebM/MP4 都没有 duration 头**（ffprobe 报 `duration=N/A`），抽帧/转码前不要依赖它；
   转完才是正常文件。

## 它到底能“动”多少：注意 Q 版角色

默认 `アイドル` / `自動まばたき` / `ランダム動作` / `ランダム口パク` / `髪の物理` **本来就是全开**
（`class="tg on"`）—— 别再点一遍，会把它们关掉。

实测自动状态下的 10 秒录像，**只有表情在变**（眨眼、随机表情），头部、头发、呼吸几乎不动。
手动把「角度 X / Y」拉到滑杆极限（−1..1）后，角色质心只移了 8px（cx 610→618），
VLM 逐帧判定「没有真正的转头，只是整体平移」。原理上它就是官宣的「パララックス+シアー」
（视差+剪切），不是 3D 头部变形，**Q 版小头大身时尤其看不出来**。

→ 要演示「头真的会转」，Anime2.5DRig 不是最佳载体，回去用 Iki 的 `ParamAngleX=30`；
Anime2.5DRig 的强项是**零配置实时表情 + 发丝跟随 + OBS 直连**。
给用户交效果时两边都跑一遍，别把「视差平移」说成「转头」。

## 所有「揺れ」都是被动跟随，没有独立时间轴（实测数字）

按区域统计 40 帧对首帧的平均灰度差（924×924 画布，CDP 连拍、间隔 0.12s）：

| 区域 | alpha 丢失时（假象） | 修好 alpha 后（自动 idle） | 修好 + 正弦驱动 |
|---|---|---|---|
| 头部（呆毛/耳/前发） | 7.35 | 7.95 | **9.00** |
| 后发 | 4.40 | 12.33 | **13.66** |
| **尾巴区** | **0.28** | 11.29 | **10.36** |
| 裙 / 腿 | 1.26 | 4.12 | **4.45** |

- 摇摆件都挂在头部/身体的运动上做从属跟随；头不转、身不晃时尾巴几乎静止。
- **某一区几乎为 0 时，先怀疑 PSD 的 alpha，再怀疑参数。** 实测尾巴区 0.28 一度被当成
  「工具不给尾巴物理」，把三档幅度全拉满仍是 0.23；真正原因是重建 PSD 时 alpha 丢了、
  只有顶层头发参与绑定。改成 RGBA 重写后同一条尾巴直接到 10.36（37 倍）。
- `bottomwear` / `legwear` 在这工具里**没有摇晃属性**，只能跟随：裙子不会自己飘、腿不会自己动
  （修好 alpha 后裙子有 4.45 的跟随量，腿/鞋依旧接近 0）。
- 每层的展开面板（层卡片里的 `button.more` ▸）只有「濃さ 0–1 / 奥行き 0–2」，
  没有幅度、频率、枢轴可调；`奥行き` 影响的是视差量，不是摆动幅度。

→ 用户要「尾巴自己摆、裙摆飘、四肢弯曲」时，这不是调参问题而是工具的物理模型问题：
  换带时间轴 / 网格顶点蒙皮的路线（StretchyStudio 的四肢蒙皮 + Spine 导出，**本机尚未实测**），
  或直接上 Live2D Cubism 骨骼。别在原地反复拉滑杆。
→ 交付话术先声明「实时视差跟随」，不要承诺独立摆动。

## 拆细层（次要手段；先看上一节深度）

> ⚠ 一度以为「后脑勺不动、尾巴尖被定住」是层块太大造成的，实测主因是每层 `奥行き` 默认值
> （`tail` 0.5 / `back hair` 0.55）。**不拆、只调深度**就能让后脑勺从静止变 32.54、尾巴根 12.96。
> 而拆层会在额头与后脑留下可见断缝（见本节末），用户会直接判「头发被切开了」。
> 只有在深度调完、仍需要更多跟随件分布时才拆。

See-through 的原始 17 层里，呆毛混在 `front hair`、鲸鳍耳混在 `headwear`、后发与尾巴各是一整块。
工具只给 15 根揺れ，症状是「后脑勺头发完全不动、尾巴尖被定住而中段像果冻」——
大块层只有外缘参与摇摆，枢轴又落在几何中心而不是连着躯干的那一端。

拆法（全部按位置 / 颜色切，不重绘）：

| 原层 | 拆成 | 判据 |
|---|---|---|
| `front hair` | `ahoge` / `side hair` / `front hair` | 呆毛 = 该层 y 顶端那一小截；侧发 = x 两侧条带且 y 过中线；中央刘海留原名 |
| `headwear` | `ears` / `headwear` | 鲸鳍耳是蓝色（`b > r+30` 且 `b > 90`），白花边留在 headwear |
| `back hair` | `back hair`(后脑勺) / `back hair_2`(中段) / `back hair_3`(发梢) | 按 y 切三段，**相邻重叠 30–40 px 防缝**；实测三段的后发运动量是单块的 3.1 倍 |
| `tail` | **不要拆**，保持整层 | 拆成根/中/梢三段反而更差：整体运动量 头部 9.00→7.95、后发 13.66→12.33，尾尖只从 2.14 到 2.33 |

结果（后发拆三段 + 尾巴保持单段，22 层）：诊断 **「29パーツ / 揺れもの31本」**，
后发从「只有边缘动」变成三段各 `後髪 · 房6`；早期把尾巴也拆三段时是 48 根，但整体指标更差。
层名带 `_2` / `_3` 会被规范化成同族，工具照样识别成同一类物理。

⚠ 拆分只增加跟随件的**数量与分布**，不改变被动跟随的本质（见上节数字）。
拆完先量一遍分区运动量再下结论，别把「层拆对了」当成「动起来了」。

**拆层的代价是缝**：`front hair` 在额头被切成 `ahoge`/`side hair`/`front hair` 三段后，用户第一眼看到的是
「额头的头发和前发不是一体的，中间有分割非常明显」；`back hair` 拆三段同样被判「背后头发出现分割」，
还会被读成「背后头发和前发同步了」。重叠 30–40 px 只能减轻、不能消除。**验收顺序是：无缝 > 会动**，
所以宁可不拆、只调深度。

**量运动量时裁剪框必须先对准层 bbox。** 反复踩的错：框落在背景或角色外，读到 0.0 就误判「没动」；
框跨到相邻层（袖口/围裙/底层身体），又把别人的运动算给这层（`topwear` 深度设 0 时躯干仍读到 11.59，
其实是底层与围裙在动）。做法：先用 `alpha > 150` 求该层真实 bbox，再往里缩 10–20 px 取框；
数字仍反直觉时，先怀疑框，再怀疑参数。

**运动量结论优先于 VLM。** 同一组帧，VLM 会把 45.40 的呆毛运动答成「没有红、没动」，
也会把分区差 30+ 的四帧答成「姿态几乎一致，像静止帧」。像素统计与热图是判据，VLM 只用于看形状是否崩。

### 写多图层 PSD：psd_tools 1.14 直接够，不必绕 pytoshop

```python
from psd_tools import PSDImage
psd = PSDImage.new(mode="RGBA", size=(W, H), color=(255, 255, 255, 0))   # 必须 RGBA
psd.create_pixel_layer(rgba_image, name="ahoge", top=0, left=0)   # 按自下而上顺序调用
psd.save(path)
```

**`mode="RGB"` 会静默毁掉全部透明层。** `PSDImage.new("RGB", …)` 建出来只有 3 个 channel
（`psd.channels == 3`），逐层 `create_pixel_layer(RGBA)` 时 alpha 被丢弃、每层都写成**整张不透明**，
一层盖一层。后果极隐蔽：读回每层 `alpha>150` 覆盖都是 **100.00%**，composite 看起来还“完整”
（因为最上面几层恰好是头发），但绑定后只有顶层头发有物理，尾巴/裙/腿全被埋死——
表现为“只有发梢在动、其它部位一动不动”。改 `mode="RGBA"`（`channels == 4`）后同一套层立刻全活。

写盘后**逐层验 alpha，别只看 composite**：

```python
assert psd.channels == 4
for l in psd.descendants():
    if l.is_group(): continue
    cov = (np.asarray(l.topil())[:, :, 3] > 150).mean() * 100
    # 覆盖 100.00% 的层 = alpha 丢了；正常层是 0.0x–11%
```

- 切层用 alpha 与布尔 mask 相乘：`a[:, :, 3] = (a[:, :, 3] * mask).astype(np.uint8)`，不另建 canvas。
- 读层内容前 `l.topil().convert("RGBA")`；**算 bbox 用 `alpha > 150`** —— 用 `>10` 会把抗锯齿噪点算进去，
  每层都报满画布，等于没测。
- 自检：重建后 `composite()` 与原 PSD 的白底合成逐像素比，均值差应主要来自背景/画框；
  角色区若出现成片 >20 的差异，就是层序或 alpha 弄错了。

## 驱动参数：idle 每帧覆盖你写的值（必须先断掉）

滑杆 id 清单（写驱动器前先 `Array.from(document.querySelectorAll('input[type=range]')).map(s=>s.id)` 确认一遍，
不同版本会增减）：

| 分组 | id: 范围（默认） |
|---|---|
| 头 | `pAngleX/Y/Z`: −1..1 (0) |
| 眼开 | `pEyeL` / `pEyeR`: 0..1 (1) |
| 视线 | `pEyeX` / `pEyeY`: −1..1 (0)；`pIrisScale`: 0.5..1.3 (1) |
| 眼差分 | `pEyeScaleL/R`: 0.5..1.5 (1)、`pEyeEase`: 0..1 (0.3)、`pEyeCY`: −1..1 (0) |
| 眉 | `pBrow` / `pBrowAngSym` / `pBrowAngL` / `pBrowAngR`: −1..1 (0) |
| 口 | `pMouthOpen`: 0..1 (0)、`pMouthForm`: −1..1 (0)、`pMouthEase`: 0..1 (0.72)、`pMouthScale`: 0.5..1.5 (1) |
| 前发 | `pFhAmp`: 0..3 (**2**)、`pFhSoft`: 0..2 (0.4)、`pBangL/C/R`: −1..1 (0) |
| 体·臂 | `pBody` / `pArmY` / `pArmPos`: −1..1 (0)、`pBust`: 0..4 (2.5)、`pBustY`: −3..3 (1) |
| 物理·小物 | `pPhysAmp`: 0..3 (**2**)、`pSoft`: 0..3 (2)、`pAccAmp`: 0..3 (**1**) |

**把三个幅度旋钮拉满能明显放大动作**（实测同一张 Q 版）：`pFhAmp=3, pPhysAmp=3, pAccAmp=3, pFhSoft=1.2, pSoft=3` 之后，
转头 ±1 的头部区均值差从 **9.90 提到 12.90**、前发摆从 5.73 到 9.74。这是不改 PSD 就能做的第一步调优，先拉满再谈「动得不够」。

直接把滑杆 `value=…` 再 `dispatch(input/change)` 基本无效：内置 idle 动画每帧重写参数。
两种错误做法都实测过：

- **关掉 `アイドル` 再设**：参数生效了，但**画面不再重绘**，三张不同角度的截图字节完全相同（cx 一丝不变）。
- **python 侧每 0.22s 设一次**：被 idle 覆盖，10 秒只漂了 2px。

正解（与 Iki 同一个配方）：**保持 `アイドル` 开**，在页面里注入 16ms `setInterval` 持续写目标值：

```js
window.__drv = setInterval(() => {
  const t = (performance.now() - t0) / 1000;
  ax.value = (0.45 * Math.sin(2*Math.PI*t/2.0)).toFixed(3);   // 摇头
  ax.dispatchEvent(new Event('input',{bubbles:true}));
  ax.dispatchEvent(new Event('change',{bubbles:true}));
  mo.value = (0.135 + 0.085*Math.sin(2*Math.PI*t/0.42)).toFixed(3);  // 咀嚼
  mo.dispatchEvent(new Event('input',{bubbles:true}));
  mo.dispatchEvent(new Event('change',{bubbles:true}));
}, 16);
```

表情预设用**键盘数字键**（通常1 / 笑顔2 / 薄目3 / 驚き4 / ジト目5 / ウインク左右 6-7），
按钮文本里虽然写着 `ジト目` 但用 `innerText==='ジト目'` 找不到（和序号在同一按钮里）。

## 能不能做出“摇头”？—— Q 版角色做不到

实测（1280 方图、17 层 PSD）：把 `角度 X` 拉到滑杆极限 ±1、甚至用 16ms 驱动器跑正弦 ±0.45，
角色质心变化只有 **2.3 px**（cx 609.5–611.8）；把 `ジト目` + 咀嚼加上后，
VLM 逐帧仍判定“没有左右摆头，只是极小的单向位移”。

原因：它就是官方说的「パララックス + シアー」，位移量按层深度分配，**Q 版小头大身时视差量被稀释到看不见**。

**已验证的放大手段**：开头那三个幅度旋钮（`pFhAmp` / `pPhysAmp` / `pAccAmp`）拉满后，
`pAngleX` ±1 时头部区均值差从 9.90 **提到 12.90**（62733 px >12），前发摆 5.73→9.74。
所以判「转头死掉」之前先把幅度拉满再量一次；但 12.90 仍只是「轻微位移 + 单侧眼/颊压缩」级别，
肉眼构不成清晰侧脸——这是 Q 版比例的上限，不是参数没调。

## 每层「奥行き」：`不动` 的真凶（已实测，优先于拆层）

层卡片 `button.more` ▸ 里只有「濃さ 0–1 / 奥行き 0–2」。`奥行き` 决定该层参与视差/跟随的量，
它给的默认值就是「谁不动」的答案：

| 层 | 默认 | 调后 | 说明 |
|---|---|---|---|
| `tail` | **0.5** | 1.6–2.0 | 全场最低 → 尾巴几乎静止的主因 |
| `back hair` | **0.55** | 1.2–2.0 | 后脑勺不动的真因 |
| `footwear` / `legwear` | 0.83 / 0.84 | 1.3–2.0 | 腿能带起来；`footwear` 实测到 2.0 仍只有 0.23（层太小，无响应） |
| `headwear` | 1.2 | 1.45 | 鲸鳍耳 / 头饰 |
| `bottomwear` | 0.88 | 1.15–1.2 | 裙摆 |
| `topwear` | 0.90 | **0~0.1** | 衣服不许跟着晃 |
| `front hair` | 1.28 | **1.0** | 最高值，收下来才不夸张 |
| `pBust` | 2.5 | **0** | 不要胸部摇曳 |

**17 层完全不拆、只调这一轮**（40 帧对首帧平均灰度差，924 画布）：

| 部位 | 默认 | 调深度后 |
|---|---|---|
| 呆毛 | — | **34.68** |
| 耳朵 | 0 | **16.97** |
| 前发 | 7.35 | **36.96** |
| 后脑勺 | 只边缘动 | **32.54** |
| 后发垂发 | 4.40 | **10.86** |
| 尾巴根 / 中段 | 0.28 | **12.96 / 9.59** |
| 尾鳍尖 | — | 2.04（枢轴问题，见下） |
| 裙摆 | 1.26 | **6.73** |
| 腿 | 1.26 | **5.96** |
| 鞋 | 0.18 | 0.23（无响应） |

→ **先调 `奥行き`，再考虑拆层**。深度调完再拆，收益很小而缝很明显。

## 尾巴枢轴落在远端：用 4×4 网格证明

尾巴横向伸出时，工具把枢轴算在**离身体最远的那一端**（尾鳍尖），于是尾梢钉死、根部甩得最凶，
看上去像「尾巴中段果冻」。层面板没有枢轴设置，改不了。

诊断法（把尾巴 bbox 切成 4×4，逐格算运动量，列 = 左右、行 = 上下）：

```
 0.0   4.2   5.1   9.8     ← 上
 3.2   3.0  14.9  16.0
 1.3   7.5  11.9  15.5
 0.0   7.2  10.0  11.2     ← 下
 ↑尾尖方向            ↑根部方向
```

左列全 0、右列最大 = 枢轴在尾尖。**拆成根/中/梢三段也救不了**（尾尖只从 2.04 到 2.33，
而头部 9.00→7.95、后发 13.66→12.33 反而更差）；要尾梢真的跟着甩，只能换能手动设枢轴的绑定
（Iki deformer / Cubism）。

→ **要“摇头 / 点头 / 真转头”的表演，必须换 Iki**（`ParamAngleX=30` 有可见偏移）。
Anime2.5DRig 的正确定位：**表情 + 眨眼 + 咀嚼 + 发丝/耳饰/尾巴物理**，用它做“拒绝/嫌弃”这类表演只靠
表情和口型就够（实测嘴区帧间差异 2.5–9.4 vs 全图 1.7–4.4，咀嚼是有效的）。

## A-pose 素材生成

见 `references/apose-generation.md`：提示词写 A-pose 一定失败（实测两次：交握→Y/V 形），
必须用自绘 COCO-18 骨架 + Union ControlNet（`type='openpose'`, strength 1.15 / end 0.70）；
SDXL 的“纯白背景”实际是冷白偏蓝 (233,242,252)，要按低饱和判定 + 边缘 flood fill 归白（thr=215）。

## 交付时给用户的话术

- 上游交 PSD（层名按上表）→ 工具自动绑定 → 出 WebM / Spine / 精灵表，这条链是通的，不是设想。
- 主动说清「闭眼闭口能自动补，但手画更好」「脖子建议并进上装」。
- 给效果必须给**动起来的实测**（四姿态对比图 + 洞率数字），不要只给一张静态截图。
- 动图必须来自**自然 idle**：撤掉所有测试驱动、姿态参数归零后重新连拍，而不是量运动量时那一版
  强制驱动（`pAngleX`/`pBody` 用 16ms 定时器推到极限拍出来，用户第一反应是「动作极其夸张」）。
- 交付播放页用本地 http（`python -m http.server` + `127.0.0.1` 地址），不给 `file://` 路径；
  并把「哪个端口是调参工具、哪个是播放器」列成表 —— 用户会同时开好几个标签，混在一起就白等一轮。
