# 验收与诊断实战规则

「看着不对」时先来这里找判据——大多数视觉判断都有可量化的像素指标。

7. **「有没有露底层」用肤色像素数判，不要问 VLM。** 统计该件 bbox 内的肤色像素数，**摆动帧不得高于静止帧**
   （实测 59 帧最大增加 0 px = 无缝；VLM 对一两像素的缝会答「没有异常」）。
   直接跑 `scripts/measure_underlayer_leak.py <帧目录>`，或传 `--bbox x,y,w,h` 指定要查的那一件。

13. **「改动是否真的落地」用像素差 delta 判，不要读代码自证。** 结构改动（换 order、换父级、换枢轴）
    后重拍同姿态截图对比，若该区差异只变化 0–2px，说明改动没生效（被覆盖 / 页面缓存 / 没重新部署），
    回去查而不是继续调参；delta 明显（例：鞋区 3423→1812）才算真改到。
    对比必须 **1:1 原生尺寸**：把 1100 的截图放大到 1280 再 diff 会凭空造出七万「模型有原图没有」的假像素，
    看着像整身错位。先 `cdp("Emulation.setDeviceMetricsOverride", width=1290, height=1290,
    deviceScaleFactor=1)`，确认 `canvas.width == model.canvas.width` 再截。

    **diff 只能算「两边都有内容」的像素**（`both = (原图非白底) & (渲染非黑底)`），这条漏掉会让整轮结论反转：
    原图是白底、播放器是黑底，背景像素差恒为 200+，不屏蔽就会被当成「模型漏画」——实测脚区
    32490px 里 90% 是背景，屏蔽后真实差异 **1916px**。同理「模型有原图没有」也要先 `~om & sm`，
    否则白色背景自己就被算成多出来的内容。

    **缓存要用 CDP 关掉，且 cache-bust URL 必须保留原参数。** 只 `Page.reload` 时文件 MD5 变了、
    四次截图却字节完全相同（被当成「改动无效」排查了好几轮）。配方：
    `cdp("Network.enable")` + `cdp("Network.setCacheDisabled", cacheDisabled=True)`，再
    `Page.navigate` 到带时间戳的 URL。⚠️ 拼 cache-bust 参数时**不要覆盖掉 `?nodrive=1`**：
    丢掉它物理就开始跑，截到的是运动中姿态（实测全图差异 41597→95829px、平均差 13.94→27.78），
    会误判成「这一版改坏了」。

15. **像素统计前先清掉页面上的说明文字。** 播放页左下角常有一行白色说明（「…都是真实物理」），
    会被算进「模型有、原图没有」：实测让多件从 71530 虚高到 73533、脚区差异从 2068 虚高到 27887，
    看着像整身错位。统计前把含该文案的 `div/p/span` 设 `display:none`，或把底部裁掉；
    报数字时说明「已隐藏页内文字」。

16. **隔离看某一层用「隐藏其他层」，不要「只留一层」。** 引擎的 view 取 parts 并集，只剩一个 part 时
    会被适配满屏（实测 163×206 的鞋铺满 1280×1280），据此算出的位置/尺寸全是假的。
    做法：`m.parts = m.parts.filter(p => p.id !== 'legwear')`，逐次少一层对比。

18. **合成偏亮是 See-through 层的固有误差，先量出来再动层级。** 拿 17 层 PSD 的 `composite()` 和
    输入原图逐像素比：实测**平均差 24.29、143270px 差异>30，整体偏亮约 25**。原因是它的层是
    「每个可见像素只归一层」，半透明边缘被多层重复计入，叠起来就偏亮。
    症状是「不管怎么调层级/枢轴，颜色都是错的、发白、像蒙了一层」——很容易误判成渲染管线或
    材质问题，其实素材颜色本身就不对。

    **颜色源的致命陷阱：`psd.composite()` 不是原图。** 实测同一套 17 层自身合成与输入原图
    平均差 24.29、143270px >30（整体偏亮约 25）。拿它当颜色源，合并层的鞋区就会显示成白色
    而不是深蓝（实测采样 (600,1050)：层 RGB [254,250,254]，原图 [34,46,90]），视觉上就是
    「鞋面被白袜盖住」。**颜色必须从原图图像文件读**（`Image.open("input/xxx.png")`），
    不能用 `psd.composite()`。

    **但绝不能整张画布无条件替换 —— 会拖出别的部位。** 各层的 alpha 都有溢出（盖到相邻部位上）：
    实测 tail 溢出 14520px x[441,631] y[732,898]（裙摆区）、handwear 5250px（躯干内侧）、
    headwear 6939px（耳区）。无条件换色后，这些溢出块显示的是「原图最终画面」即上层的内容，
    该层一摆动就把别人的身体拖出来 —— 用户判「衣服(胳膊)、耳朵、尾巴跟都有多余身体粘连」。
    正确判据：**本层颜色 ≈ 原图**（差异≤60）才算它自己的内容，才换色；差异大的一律保留本层原色。
    另外 under-paint 过的层（给耳朵洞填头发纹理的 headwear）必须整层跳过，否则填好的头发会被
    原图的耳朵盖回去，形成「耳朵原始图层没清理掉」的重影。
    分区替换后全图差异会从 1.07 回到 3.94，但粘连消失——**优先级是结构正确而非像素最小差**。

    **修法：alpha 保留分层结果，RGB 按「是否本层内容」分区换成原图。**
    ```python
    ref = np.asarray(Image.open("input/原图.png").convert("RGB"), dtype=np.uint8)
    for name, im in out.items():
        a = np.asarray(im.convert("RGBA")).copy()
        if (a[:, :, 3] > 0).sum() == 0: continue
        a[:, :, :3] = ref          # 每层只贡献「这块归我」的形状
        out[name] = Image.fromarray(a, "RGBA")
    ```
    这一条把全图差异从 **43386px / 平均差 14.97 降到 4429px / 1.53**；配上白底后 **5481px / 1.07**，
    脚区 **43px**（原 3778px）、领口 **16px**（原 1754px）。
    验证：改完 PSD 自己的 `composite()` 应与原图逐像素一致（实测角色区平均差 0.03、>30 为 0px）。
    不要再试 alpha-bleed 把边缘浅色换成内部色——实测差异反而升到 19618px，因为原图边缘本来就是浅色抗锯齿。

23. **补色 / under-paint 的「覆盖率阈值」会把整段静默跳过。** 曾写：「若 back hair 在本区覆盖 >30% 才用它补色」，
    而实测 back hair 覆盖 17.6%、front hair 13% → `src=None` → **整段填充根本没执行**，什么都没改，
    而层数和覆盖率都正常，极难发现。症状是「改了但画面一点没变」。
    守则：阈值判空时至少打一行 `!! src=None`；能直接挖空（alpha=0，让下层显示）就不要补色 ——
    耳朵区实测下面本来就有 back hair 6802px + front hair 5055px，挖空就是对的。

27. **「某层半透明」先查是谁盖住它，不要先抬 alpha。**

    症状：「脖子半透明了」，同时 PSD 里 neck 层 alpha 已是 100% 不透明。
    实测 y=428 一行有三层 alpha=255：
    ```
    neck     RGB (225,166,145) 肤色   order 4   ← 正确答案
    topwear  RGB (187,179,213) 灰紫   order 8   ← 盖在上面
    back hair RGB (46,74,150)          order 0
    ```
    **上衣的 order 高于脖子，把脖子整片盖成了灰紫**。See-through 把「下巴到领口」这段同时归给了 neck 和 topwear，
    而 topwear 那块的 RGB 是它自己的偏亮底色（分区换色时因差异>60 被保留）。
    抬 alpha 完全无效（它本来就不透明）；改这些像素的颜色也不对。**应该把 topwear 在脖子处挖掉。**

    挖的时候也不能整块挖：neck 的 bbox 一直延伸到 y=454，而 y 438–454 那段在原图里是**衣领/领结（深色）**。
    整块挖会把衣领变成肤色。判据：**只在「原图颜色 ≈ neck 自身颜色」处挖**。

    同理，抬 neck 的 alpha 也要用这个判据：neck 3766px 里只有 542px 是「原图确实显示脖子」的地方，
    其余本来就被衣领盖住（是备用内容）。全抬满会把描边变实心暗块。
    排查序：①先量每行有哪几层 alpha=255 → ②看谁 order 更高 → ③比「本层 RGB vs 原图 RGB」定哪层才是该显示的

29. **「看着缺一块」先回原图量同一处；原图本来就这样就不是 bug。** 实测左鞋后帮「缺一块」，
    该区原图白色(袜) 1616px > 深蓝(鞋) 1381px —— 白袜本来就压在鞋后帮上，模型层级是对的。
    判法：隐藏上层后若该件立刻变完整 → 是被上层盖住；再看原图同位置颜色占比决定是素材特征还是真错。
    两种可能都报给用户选，不要自己「修」掉原画的设计。
    三方对比（原图 / PSD 自身合成 / 模型渲染，同一原生尺寸）能一次定位是谁的错：
    PSD 对而模型错 = 渲染管线；PSD 就错 = 素材或层序（实测脚区 PSD↔原图 4007px、模型↔PSD 24651px）。
    另：`crop_to_alpha(soft=8)` 会让 part bbox 每边大 8px，纹理与 mesh 一起偏移，**渲染不错位**，
    不要拿 ±8px 的 bbox 差当 bug 追；要看渲染后的 bbox 是否与原图一致。

## 用户一定会问的三个入口（先讲真相，再改）

33. **VLM 会把原图本来就有的描边当成「多余的线」。像素���行比对才算数。**

    用户报「多出一条黑线」，VLM 连续两次确认「有」，而实测：
    · 腿区像素差异只有 **30px**
    · 逐行比对原图与渲染的「暗像素组」，y 890–1114 共 29 行**全部 ok**（每组起止完全一致）

    可靠的验收写法 —— 按行提取「暗像素成组」后逐组对比，直接输出 `ok / 多: [...]`：
    ```python
    def dark_groups(img, y, lo, hi, th=110):
        xs = [x for x in range(lo, hi) if img[y,x].mean() < th]
        # 聚类成段，间隔>3 断开
    for y in range(890, 1120, 8):
        go, gs = dark_groups(orig,y,...), dark_groups(shot,y,...)
        extra = [g for g in gs if not any(overlap(g, o) for o in go)]
    ```
    这比「看图像」准得多，而且能直接指出差在哪一行哪一段。

34. **「某层上多了一条线」先查谁盖在它上面，不要先改这层自己。**

    用户报「左边的腿还是有一条线，跟之前耳朵那样的边缘问题」。我先去改腿层自己的边缘（抹掉描边），
    结果描边 (74,71,72) 变 (250,246,250) 白，腿边缘成了一条白边，**比原来的黑线更难看**，
    而且动态指标从 121 只降到 80 条/帧。

    真实原因是**裙子**：
    ```
    (646,894)  原图 (113,85,82) 暖肤色   →   渲染 (24,39,43) 暗
       leg_R       alpha=255 RGB(113,85,82)   ← 腿层完全正确
       bottomwear  alpha=243 RGB(22,38,42)    ← 裙子错拿了这块，order 又高于腿
    ```
    See-through 把裙摆下沿那一圈腿也算进了 bottomwear。
    判据：`bottomwear 有像素 & 该处有腿 & |bottomwear_rgb - 原图| > 40` → 挖掉。实测挖 2383px。

    **效果（同一套指标）：**
    ```
                                  改前    改后
    腿层 mask 内差异              543px  160px
    y800–919 区段                397px   36px
    全图平均差                    3.39    3.32
    ```
    这已经是第三次同一个模式（脖子被 topwear 盖、耳朵底下有静态耳朵、腿上有条线）——
    **先查「谁盖在我上面」，再查「我自己的像素」。**

35. **压在画面上的「多出线条」指标会把裙子摆动算进来，不能用它判腿。**

    我用「动态帧 vs 原图，逐行比暗像素组」当指标，得到 121 条/帧，以为是腿摆出来的。
    把腿摆幅从 ±5 压到 ±3 后，指标反而升到 123.8 条/帧——**说明它根本不是摆幅造成的**。
    原因：该统计的 x 范围 540–820 把裙子摆动全算进去了。
    正确口径：**限制在该 part 自己的 mask 内做统计**（从 PSD 读 alpha 当范围）。

36. **「残留的裁剪边缘」= 摆动时两腿被拉开，间隙被撑宽。看间隙宽度，别看差异像素。**

    用户报「刷新网页后还是有，就好像是残留的裁剪边缘」。静态差异只有 428px（与已接受版本持平），
    所以不是静态。换了一个硬指标 —— **分界带最大连续空白宽度**，一眼看出：
    ```
    y=930   原图 18px → 摆动帧 25px (+7)
    y=1020  原图 34px → 摆动帧 44px (+10)
    y=1050  原图 47px → 摆动帧 58px (+11)
    ```
    根因：两腿吃不同输入（BodyAngleX 0.85 vs AngleZ 0.9），相位不同⇒往相反方向分⇒缝被撑宽。
    改为**同源输入**（都吃 BodyAngleX 0.9，只留 scale 24/21 的幅度差）后：
    ```
    y=930  +7→+4    y=990  +9→+4    y=1050  +11→+4
    动态平均与原图持平（+0/-1）
    ```
    **这个指标比「差异像素数」灵敏得多**：后者对 7-11px 的缝宽变化几乎不敏感（427 vs 428）。
    判定「分界处有问题」时，直接量「最大连续空白宽度」并与原图比。

37. **羽化两个坑：一半被裁掉、两层都羽化会透底。**

    坑一：`m_back = upper & (xx >= split_x)` 导致后腿只在分界右侧有 mask，
    羽化带被裁掉一半 —— 实测每行只剩 **1-2px 半透明**，视觉上仍是硬边。
    必须让 `m_back` 向左扩 FEATHER 像素。

    坑二：两层各自 smoothstep 时叠加 = `1-(1-a)(1-b) < 1`（a=b=0.5 时只有 0.75），
    接缝变半透明直接透底。
    **正解：只羽化前腿，后腿保持 alpha=1 兜底** —— 叠加恒为 1，而前腿边缘仍是柔的。

    另：`m_front` 不能跟着向右扩 FEATHER（会多拿后腿内容），实测腿区差异 404→532px。

38. **当「像素数据说好了、VLM 说没好」时，不要无限迭代 —— 交出数据让用户裁定。**

    最后一轮：静态腿区 401px（历史最低，全图 3.31）、分界缝 +4px（从 +11 降下来）、
    叠加覆盖 99.8%。但 VLM 仍说「空白更宽、有硬直线切口、不自然」。
    它在看**摆动帧**，把腿本身的位移（8-14px）描述成「空白更宽」——这是运动，不是缺陷。
    连续 8 版（v53–v60）都在和 VLM 的描述搏斗，而它每次的措辞几乎不变。
    正确做法：把 4 个版本的可回退文件都留着，列出各自的数据，让用户自己看、自己选。

39. **alpha 羽化 = 两层颜色混合 = 视觉上融合成一条。想“分开”就不能羽化。**

    为了消除硬边，我把前腿右边缘做了 6px alpha 渐变。结果叠合公式
    `result = legR*a + legL*(1-a)` 在 a=0.5 处把两腿颜色各掺一半，
    **视觉上直接融合成一条腿** —— 用户：「你这又退化了啊 双腿现在又回到没分开的情况了」。

    **关键区分：「图层分开」≠「视觉上分开」。**
    两层确实是独立的 part、独立 deformer、各自 param，但像素掺混后眼睛看到的就是一条。
    → **接缝靠重叠带宽解决，不靠 alpha 羽化**。

    **另一个陷阱：同源输入会把两腿变成同步摆。**
    为了让缝不被撑宽，我让两腿都吃 `ParamBodyAngleX`，结果它们完全同步，
    动起来就是一条腿在摆（用户同样报「没分开」）。
    正确的取舍：**异源输入（不同相位）+ 后腿幅度压到前腿的 60%** ——
    前腿摆开时露出的那块（leg_L）几乎不动，所以露出的内容仍是原图。

    实测最终状态（v61）：
    ```
    参数相关 r=0.746（异相位，视觉上确实是两条腿在各自动）
    腿L ±0.98 / 腿R ±1.31（后腿幅度只有前腿 60%）
    分界缝 +4~6px（原图基准）
    静态腿区 401px（历史最低）
    ```

    **验收口径要一起看两个数：**
    · 参数相关 < 0.85 → 两腿真的在分头动（不是同步）
    · 分界缝宽度 ≈ 原图 → 没有把间隙撑开
    只看其中一个都会调错方向（看缝→改同源→融合；看相关→改异源→撑缝）。

40. **`fill_alpha` 里改的 RGB 可能是死代码 —— 先查它后面有没有被用到。**

    我在 `split_legs.py` 里花了几轮写「补色取样要跳过描边」，结果 `rgb` 这个变量
